WHAT IT MEANS
Your DB has fresh data.
Your cache has stale data.
A user reads from cache and gets wrong data.
Hard to reproduce. Hard to catch.
REAL PRODUCTION DANGERS
💸 OLD PRICE — item costs $29 in DB, cache says $49. User overcharged.
🔐 OLD PERMISSION — user was banned, cache still says "admin".
📦 OLD INVENTORY — 0 items in stock, cache says 5. Order placed.

STRATEGY 1: TTL
TIME-TO-LIVE — PASSIVE EXPIRY
TTL METHOD PASSIVE
HOW TTL WORKS
Every cache key gets an expiry time.
Key auto-deletes when TTL hits zero.
Next request: cache miss → fetch DB.
SET price:42 "$29.99" EX 300
EX 300 = expires in 300 seconds
TTL COUNTDOWN (300s window)
price:42
TTL: 300s
t=0 SETt=150st=300s EXPIRED
⏱ Stale window = up to 300s
✓ PROS
Simple to set up
Zero extra code
Works everywhere
✗ CONS
Still stale until
TTL expires
Wrong TTL = pain
BEST USE CASES
✓ Non-critical data (weather, blog posts)
✓ Reads far outnumber writes
✗ NOT for prices, permissions, stock
TTL CHEATSHEET
Static assets / config 7 days
Product details 5–30 min
Prices / inventory 30–60 sec
Permissions / auth DON'T TTL

STRATEGY 3: WRITE-THROUGH
Every write goes to cache AND DB
together. Cache always in sync.
Reads always fast. Writes slower.
cache.set("price:42", 29.99)
db.update("price:42", 29.99)
Both happen in the same write operation
