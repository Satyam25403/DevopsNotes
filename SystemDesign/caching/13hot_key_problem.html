That key lives on one shard, one node.

FIX 1: L1 LOCAL
REPLICA
CACHE ON EACH APP SERVER — SKIP REDIS
LOCAL REPLICA FIX SOLUTION 1
THE IDEA
Each app server holds a local in-process copy
of the hot key (HashMap / Guava cache).
TTL: 1–5 seconds. Redis hit rate: near 0.
Slightly stale — acceptable for leaderboards.
// Each app server has its own L1 cache
const L1 = new LRUCache({ ttl: 2000 }); // 2s

async function getLeaderboard() {
  const local = L1.get("leaderboard");
  if (local) return local; // L1 HIT
  const data = await redis.get("leaderboard");
  L1.set("leaderboard", data); // store
  return data;
}

FIX 2: KEY SHARDING
SPLIT THE KEY ACROSS N REDIS NODES
KEY SHARDING FIX SOLUTION 2
THE IDEA
Instead of one key on one node,
create N copies across N nodes.
Each request picks a random shard.
Load spreads evenly across the cluster.
// One key on one node — dangerous:
GET leaderboard:global

// Sharded across N=4 nodes:
shard = Math.floor(Math.random() * 4);
GET leaderboard:global:shard:{shard}

// Write: update all N shards
for i in range(4):
  SET leaderboard:global:shard:{i} data
