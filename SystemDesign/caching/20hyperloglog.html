THE TRICK: LEADING ZEROS IN HASHES
INTERNALS PROBABILITY
127.0.0.1:6379> _
▸ each element is hashed → binary analyzed
ELEMENT → HASH → LEADING ZEROS → REGISTER
THE INTUITION
if you flip a coin and get 10 heads in a row,
you probably flipped ~1024 coins total.

HLL does this with leading zeros in hashes.
more leading zeros seen = larger cardinality.
🎲
MAX LEADING ZEROS SEEN: 0
probability of k leading zeros
= 1 / 2^k → estimate = 2^k
▸ 16,384 registers track max leading zeros per bucket
16,384 registers × 6 bits = 12 KB total
hash → count leading zeros → update register
max leading zeros seen estimates cardinality.
16K registers averaged → 0.8% error rate.

WHEN TO USE · WHEN NOT TO

📊 UNIQUE PAGE VIEWS
PFADD hll:page:{id} {visitorID}
PFCOUNT hll:page:{id} → ~uniques today
one 12KB key per page per day · exact enough
🔍 UNIQUE SEARCH QUERIES
track distinct queries seen per hour.
detects query volume spikes, trend shifts.
0.8% error irrelevant at analytics scale.
🧪 FUNNEL ANALYSIS
PFMERGE hll:funnel:checkout hll:step1 hll:step2
union of users who hit each step.
drop-off = PFCOUNT(step1) - PFCOUNT(step2)
✗ WHEN NOT TO USE
• need EXACT count → use a SET or counter
• need to list who is in the set → HLL can't do that
• deduplicating payments / transactions → too risky at 0.8% error
• small cardinality (<1000) → plain SET is fine
