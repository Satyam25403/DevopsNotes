WHAT IS A COLD CACHE?
New deployment → cache is empty.
Every request = cache MISS.
All misses → DB gets 100% of traffic.
DB buckles. Users see timeouts.

3 WARMING STRATEGIES
PICK THE ONE THAT FITS YOUR SYSTEM
STRATEGIES PICK ONE
📼
STRATEGY 1: REPLAY READS
Log all DB reads for the last hour.
Before deploy: replay those reads into
the new cache instance. Go live warm.
# Before deploy script
cat read_log_last_1h.txt |
  xargs -I{} redis-cli GET {} >/dev/null
✓ Real traffic shape
✓ Warms exact keys
⚠ Needs read logging
⚠ Replay takes time
🔢
STRATEGY 2: PRE-LOAD TOP-N
Query DB for the top-N most accessed
records. Background job loads them into
cache before traffic is switched over.
top_keys = db.query(
  "SELECT key FROM access_log
   ORDER BY hits DESC LIMIT 10000")
for k in top_keys: cache.set(k, db.get(k))
✓ Simple to implement
✓ No log needed
⚠ Warms only hot keys
⚠ Not traffic-shaped
🔄
STRATEGY 3: DUAL-RUN OVERLAP
Keep OLD deployment running in parallel
while new one warms up organically.
Switch traffic only when new hit rate ≥80%.

WHICH ONE TO USE?
Small system: Top-N pre-load is enough
Medium: Replay reads + TTL jitter
Critical system: Dual-run + health gate
Always combine with TTL jitter too.
