# Terraform State Management

## How State Works

Terraform makes changes by comparing **current state** and **desired state**. The `terraform.tfstate` file is the **state file** — it holds the actual, real-world state of your infrastructure. Every `terraform apply` reads this file, diffs it against your `.tf` configuration, and only acts on the delta.

---

## State File Best Practices

### 1. Use Remote Backend Storage

When you run Terraform commands, the state file is created and stored **locally** by default — but this is not a best practice for team environments. Instead, store the state file in a **remote backend** such as:

- AWS S3 bucket
- Azure Blob Storage
- GCP Storage Account

**How it works with a remote backend:**

```
run tf commands -> access state file from remote -> run it as local -> make changes to infra
```

This ensures everyone on the team is always working against the same source of truth.

### 2. Never Manually Edit the State File

Do not update or delete `terraform.tfstate` manually. Doing so will **corrupt the file**, causing Terraform to lose track of what's actually deployed and potentially leading to duplicate or orphaned resources.

### 3. Enable State Locking

Since the state file is centrally stored, multiple people may try to run Terraform simultaneously, which can lead to **inconsistent state**. State locking prevents concurrent operations — only one process can hold the lock at a time.

> Most remote backends (S3 + DynamoDB, Azure Blob Storage, etc.) support state locking natively.

### 4. Isolate State Files per Environment

Each environment (DEV, UAT, SIT, DR, PRE-PROD, PROD) should have its **own separate state file**. Mixing environments into a single state file is a recipe for accidental cross-environment changes.

### 5. Take Regular Backups

Accidental deletion or corruption of the state file means losing the record of your actual/current infrastructure state — Terraform would no longer know what it manages. Enable versioning on your remote storage (e.g. S3 versioning, Azure Blob soft delete) so you can recover from mishaps.

## Setting Up a Remote Backend on Azure

The storage that holds your remote state should **not** be managed by Terraform itself — it needs to exist before Terraform runs. Create it separately using the Azure CLI, the Azure Portal, or a bootstrap script.

### Bootstrap Script (`storage.sh`)

```bash
#!/bin/bash

RESOURCE_GROUP_NAME=tfstate-day04
STORAGE_ACCOUNT_NAME=day04$RANDOM   # $RANDOM ensures a unique name
CONTAINER_NAME=tfstate

# Create resource group
az group create \
  --name $RESOURCE_GROUP_NAME \
  --location eastus

# Create storage account
az storage account create \
  --resource-group $RESOURCE_GROUP_NAME \
  --name $STORAGE_ACCOUNT_NAME \
  --sku Standard_LRS \
  --encryption-services blob

# Create blob container
az storage container create \
  --name $CONTAINER_NAME \
  --account-name $STORAGE_ACCOUNT_NAME
```

Run this **once** before any Terraform commands. It provisions the storage account and container that will hold all your state files going forward.

## Connecting Terraform to the Remote Backend

Once the storage account exists, configure Terraform to use it via the `backend "azurerm"` block. Terraform connects to the storage account using the **Access Key** for authentication.

**main.tf:**
```hcl
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.8.0"
    }
  }

  backend "azurerm" {
    resource_group_name  = "tfstate-day04"
    storage_account_name = "day0417691"       # The name generated by $RANDOM in your script
    container_name       = "tfstate"
    key                  = "dev.terraform.tfstate"  # State file name inside the container
  }

  required_version = ">= 1.9.0"
}
```

After running `terraform init` with this configuration, you will see a `dev.terraform.tfstate` file created inside the Azure Blob container. That file is now accessed **as if it were local** every time Terraform runs — the remote/local distinction is transparent to the rest of your workflow.

You can then provision infrastructure as normal:

```hcl
resource "azurerm_resource_group" "example" {
  name     = "example-resources"
  location = "East US"
}

# ... more resources
```

```bash
terraform init      # Downloads provider + connects to remote backend
terraform validate
terraform plan
terraform apply
```

> **Tip:** For different environments, change the `key` value — e.g. `dev.terraform.tfstate`, `staging.terraform.tfstate`, `prod.terraform.tfstate` — while reusing the same storage account and container. This satisfies best practice #4 (isolation per environment) without needing separate storage accounts.
