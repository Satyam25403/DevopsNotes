STICKY SESSIONS & WHEN TO USE WHAT
STICKY SESSIONS DECISION GUIDE
Sticky sessions pin a client to a backend. It's a trap.
COOKIE-BASED STICKY SESSIONS
# ALB stickiness cookie
Set-Cookie: AWSALB=AbC123xYz; Path=/; HttpOnly
→ client always routed to backend-2
✓ Useful for server-side session state.
✗ Backend dies → session lost anyway.
✗ Uneven load distribution.
BETTER: SHARED SESSION STORE
# Store session in Redis, not backend RAM
session = redis.get("sess:AbC123")
→ any backend can serve any client
✓ Any backend handles any request.
✓ True horizontal scaling.
✓ Session survives backend restart.
WHEN TO USE WHICH
USE NLB (L4)
Non-HTTP protocols
UDP / raw TCP
Gaming / IoT / gRPC
Static IP required

USE ALB (L7) ✓
HTTP / HTTPS
Microservices

INTERVIEW ANSWER
"Default to ALB for HTTP. NLB only for non-HTTP or static IP requirements. Offload TLS at the LB, manage certs centrally in ACM. Replace sticky sessions with Redis for true stateless backends."
Sticky sessions create hot spots. Shared Redis sessions scale cleanly.
Stateless backends + external session store = true horizontal scale.
