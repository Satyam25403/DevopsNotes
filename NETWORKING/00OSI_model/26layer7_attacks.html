01
The app builds a SQL query by concatenating user input directly into the string. The database can't distinguish "data" from "SQL code" — they're both just text arriving from the app.
02
The apostrophe (') closes the string literal. Then OR 1=1 makes the WHERE clause always true. Then -- comments out the rest. Every row returns. All users dumped.
03
Beyond data dump: UNION-based SQLi extracts other tables. Blind SQLi infers data from true/false responses. Error-based leaks schema. SQLMap automates all of these.
WHY IT WORKS
The database trusts whatever the app sends it
The app and DB have an implicit trust relationship. If the app sends "SELECT * WHERE 1=1", the DB executes it — no questions asked. The fix is simple: stop building queries from strings.

01
XSS injects malicious JavaScript into a web page that other users load in their browser. The browser trusts the page's domain — so the injected script runs with full site permissions.
02
A stored XSS in a comment field runs for every single visitor who views that comment. Script can steal session cookies (document.cookie), redirect to phishing pages, log keystrokes, or hijack form submissions.
03
The Samy worm (2005): stored XSS on MySpace spread to 1 million users in 20 hours. Self-replicating. Added attacker as "friend" on every visit. Largest XSS outbreak ever.
XSS IMPACT
Script runs with victim's session, on victim's machine
Attacker doesn't need your password if they have your session cookie. document.cookie sent to attacker.com = full account access. No login needed.

HOW TO DEFEND
PARAMETERIZED QUERIES · CSP · ESCAPING
DEFENSES FIX IT
DEFENSE: PARAMETERIZED QUERIES
❌ VULNERABLE (string concat)
query = "SELECT * FROM users WHERE name = '" + userInput + "'"
✓ SAFE (parameterized)
query = "SELECT * FROM users WHERE name = ?"
db.execute(query, [userInput])
# DB treats userInput as PURE DATA
# ' OR 1=1 -- is just a username, not code
🛡
PARAMETERIZED QUERIES
Separate SQL code from data. Use PreparedStatement (Java), ?/%s placeholders (Python), ORM frameworks. The single most important SQLi fix.
🔒
OUTPUT ENCODING (XSS fix)
Always HTML-encode before rendering user content. < → &lt; makes <script> display as text, not execute. Use template engines that auto-escape by default (Jinja2, React JSX).
📋
CONTENT SECURITY POLICY (CSP)
HTTP header that tells browser which scripts to trust. Content-Security-Policy: script-src 'self' blocks all inline scripts and third-party sources. Stops most XSS execution even if injection succeeds.
🍪
HttpOnly + SameSite COOKIES
HttpOnly flag: JS can't read session cookie — stops XSS cookie theft. SameSite=Strict: cookie not sent cross-site. Together: XSS impact dramatically reduced even if script runs.
THE RULE
Never trust user input. Validate, escape, parameterize.
For SQLi: parameterized queries. For XSS: output encoding + CSP. For both: input validation + WAF. Test with OWASP ZAP or Burp Suite. Ship nothing without it.
