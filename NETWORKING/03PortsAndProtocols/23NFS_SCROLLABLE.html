▸ WHAT IS THE SUID BIT?
When a binary has the Set-UID permission bit set,
it executes as its owner's UID — not the caller's.
If owner = root and SUID is set → always runs as root,
regardless of who launches it.

root@attacker:~# cp /bin/bash /mnt/nfs/rootbash

The SUID binary now lives on the server's disk, owned by root, executable by anyone.

👤 FIX 1 — use root_squash (default)
/srv/nfs 192.168.1.0/24(root_squash,rw)
# UID 0 → mapped to nobody (65534)
root_squash is the default — only set no_root_squash when explicitly required, and never on world-accessible exports.
🌐 FIX 2 — restrict exports to specific IPs
# replace * wildcard with subnet/IP
/srv/nfs 192.168.1.10(rw,root_squash)
Wildcard * lets any host on any network mount. Even with root_squash, data exposure risk remains. Limit to known IPs and firewall port 2049.
🚫 FIX 3 — nosuid on client mount
# /etc/fstab on client
server:/share /mnt nfs \
  nosuid,noexec,ro 0 0
nosuid makes the kernel ignore SUID bits on the mounted filesystem. noexec prevents running binaries at all. Defense in depth on the client side.
🔐 FIX 4 — NFSv4 + Kerberos (krb5)
# /etc/exports with sec= option
/srv/nfs *(rw,root_squash,sec=krb5p)
# krb5p = authenticate + encrypt
NFSv4 with Kerberos authenticates the user identity cryptographically — the server no longer trusts the client's claimed UID. krb5p also encrypts data in transit.
CONTROL EFFECTIVENESS vs THIS ATTACK
root_squash + nosuid + IP restriction eliminates this attack path entirely.
NFSv4 + Kerberos removes UID trust from the equation — cryptographic identity only.
