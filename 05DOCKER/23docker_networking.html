BRIDGE NETWORK
ISOLATED SUBNET · NAT · PORT PUBLISHING
MODE 1 DEFAULT
BRIDGE NETWORK — ISOLATED SUBNET + NAT
BRIDGE NETWORK PROPERTIES
✓ Containers get private IPs (172.17.0.x) isolated from host
✓ Containers on same bridge talk directly by name (DNS)
✓ External access via port publishing: -p host:container
⚠ NAT overhead for every external packet (minor)
✕ Default bridge: no automatic DNS. Use custom bridges instead.
# default bridge (no DNS between containers)
docker run --network=bridge nginx
# custom bridge (DNS by container name) ← recommended
docker network create myapp
docker run --network=myapp --name=db postgres
docker run --network=myapp --name=api -p 3000:3000 node
# api can reach db by name: postgres://db:5432
!
Default bridge doesn't support DNS. Always create a custom bridge network — then containers discover each other by container name. docker-compose does this automatically.
BRIDGE NETWORK
Isolated subnet + NAT. The right default for most apps.
Use bridge for: web apps, databases, microservices. Create a custom bridge (not the default one) to get automatic DNS resolution between containers by name.

HOST NETWORK
SHARES HOST STACK · NO ISOLATION · MAX PERFORMANCE
MODE 2 NO ISOLATION
HOST NETWORK — CONTAINER IS THE HOST
HOST NETWORK PROPERTIES
✓ No NAT — fastest possible network performance
✓ No -p flag needed — container ports = host ports directly
✕ No network isolation — container can access all host ports
✕ Port conflicts: two containers can't use same port
⚠ Linux only — no effect on Docker Desktop (Mac/Windows)
💡
When to use host: network-sensitive monitoring tools (Prometheus node_exporter), high-throughput proxies (Nginx), anything where NAT overhead matters. Never use for untrusted code.
!
On Docker Desktop (Mac/Windows) host networking is silently a no-op — there's a Linux VM in between. Your container still gets isolated. Only meaningful on bare Linux hosts.
HOST NETWORK
Zero NAT. Container IS the host network.
Use for: network monitoring, high-throughput proxies, when every microsecond matters. Never for web apps or databases — too much blast radius if container is compromised.

WHEN TO USE EACH
🌉
BRIDGE → Web apps, APIs, databases
docker-compose default. Custom bridge for DNS. -p for external access. 99% of use cases.
⚡
HOST → Monitoring, high-throughput proxies
Prometheus node_exporter, performance-critical services. Linux only. Trusted workloads.
🚫
NONE → Offline batch jobs, security sandboxing
ML training, data transformations, cryptography operations, untrusted code execution.
☁
OVERLAY → Multi-host Swarm / Kubernetes
When containers span multiple Docker hosts. VXLAN tunnel. Used by docker swarm and flannel/calico in K8s.
💡
In docker-compose, all services automatically join a custom bridge network named [project]_default. DNS works by service name. No configuration needed — this is the right default.
NONE NETWORK
Total isolation. Only loopback. Maximum security.
docker run --network=none is the strongest isolation Docker offers. No packets in or out. Use for untrusted code, compliance-sensitive batch jobs, or anything that should never phone home.

COMMANDS CHEAT SHEET
Docker Networking Cheat Sheet
# list all networks
docker network ls
# inspect network (see containers + IPs)
docker network inspect myapp
# create custom bridge (with DNS)
docker network create --driver bridge myapp
# connect running container to network
docker network connect myapp container-name
# debug: exec into container, test connectivity
docker exec -it api sh
ping db # works if on same custom bridge
curl http://db:5432 # connect by name
# check container network settings
docker inspect container --format '{{json .NetworkSettings}}'
# prune unused networks
docker network prune
COMMON GOTCHAS
① Default bridge has no DNS — containers can't find each other by name. Always create a named network.
② --network=host silently ignored on Mac/Windows Docker Desktop. Works only on Linux.
③ -p 3000:3000 vs EXPOSE 3000 — EXPOSE is documentation only. -p actually publishes.
④ docker-compose auto-creates a network. Services reach each other by service name, not container name.
RULE OF THUMB
docker-compose + custom bridge covers 99% of cases
If you're using docker-compose, you already have correct networking. If running standalone containers, create a named bridge network first, then --network=[name]. Never use default bridge for production.
