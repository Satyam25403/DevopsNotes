PART 1 OF 4 overlay2
🗂 ONE VIEW, MANY LAYERS
Docker uses OverlayFS (overlay2 driver) to stack read-only image layers and a writable container layer into a single unified filesystem. The container sees one clean directory tree — it has no idea it's built from stacked layers.
OVERLAYFS MOUNT — THREE DIRECTORIES
lowerdir
Stacked read-only image layers. Shared across ALL containers using the same image. Never written to.
upperdir
Writable layer unique to this container. Starts empty. Only grows when files are modified or created.
merged
The unified view the container sees. OverlayFS presents upperdir on top of lowerdir — seamlessly.
Image layers are shared. Only changed files live in upperdir.
10 containers from the same image → 10 upperdirs, 1 shared lowerdir.

PART 2 OF 4 CoW
✏ COPY-ON-WRITE EXPLAINED
When a container reads a file, it reads directly from lowerdir — no copy. When it writes a file for the first time, OverlayFS copies the entire file up to upperdir first, then writes the modified version there.
COPY-ON-WRITE SEQUENCE
✓ WHY IT'S FAST
Reads are free. No copy needed. 10 containers share 1 set of image layer files on disk.
⚠ LARGE FILE TRAP
Modifying a 500MB file copies the whole thing to upperdir first. One byte change = 500MB copy-up.
Read from lowerdir for free. First write triggers a full file copy-up.
lowerdir is never modified. It stays shared and clean forever.

PART 3 OF 4 GOTCHA
⚠ DELETING DOESN'T FREE SPACE
When a Dockerfile RUN rm -rf /tmp/bigfile runs in a new layer, the original file still exists in the earlier layer. OverlayFS adds a whiteout file to hide it — but the bytes are still on disk.
WHITEOUT — THE HIDDEN SPACE WASTE
✓ THE FIX — CHAIN RUN COMMANDS
✗ RUN apt-get install gcc
RUN make build
RUN apt-get remove gcc ← wastes space
────────────────────────────
✓ RUN apt-get install gcc \
&& make build \
&& apt-get remove gcc ← ONE layer
Deleting in a new layer adds a whiteout — original bytes persist in earlier layer.
Chain installs and cleanups in a single RUN to keep layers lean.
