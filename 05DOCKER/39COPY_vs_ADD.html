COPY: BUILD CONTEXT → IMAGE LAYER
WHAT COPY DOES
Takes files or directories from your build context and places them into the image. That's it. No surprises. What you see is what you get — and Docker can cache it reliably.
COPY src dst — copies files from build context into the image.
Explicit, predictable, cache-friendly. Always prefer COPY.

ADD: THREE BEHAVIOURS IN ONE COMMAND
Dockerfile — ADD examples
# ① like COPY (fine but unnecessary)
ADD src/ ./src/
# ② auto-extracts archive (hidden!)
ADD app.tar.gz /opt/app/
# ③ fetches URL — BUSTS CACHE!
ADD https://example.com/file /opt/
ADD does three things: copy files, auto-extract tars, fetch URLs.
The extra powers hide intent and break the build cache.

⚠ TAR GOTCHA TOO
ADD archive.tar.gz /opt/ looks like a simple copy but silently extracts the archive. A reader has no idea what ends up in /opt/ without inspecting the tar. Hidden behaviour = harder to review.
✓ THE FIX FOR URLs
Use RUN curl -fsSL URL -o /opt/file instead. The layer is explicit, the intent is clear, and caching behaves correctly based on the Dockerfile instruction itself.
ADD with a URL fetches live on every build — no cache ever hits.
Silent URL fetches = unreproducible, unauditable images.

THE GOLDEN RULE
Use COPY by default.
Reach for ADD only when you need
automatic tar extraction.
Never ADD a URL. Use RUN curl/wget instead.
correct Dockerfile
# ✓ files — always COPY

Explicit Dockerfiles are auditable, cacheable, reproducible.
