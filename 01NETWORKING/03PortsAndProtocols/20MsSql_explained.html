▸ xp_cmdshell — the dangerous stored procedure
WHAT IT IS
xp_cmdshell is a built-in MSSQL extended stored procedure.
it passes a string directly to the Windows command shell
and returns the output as SQL rows.

disabled by default since SQL Server 2005 —
but it can be re-enabled in two SQL statements
by anyone with sysadmin privileges.
▸ what an attacker can do once enabled
① READ ANY FILE ON THE SERVER
execute OS commands → read sensitive files, credentials, configs stored outside the DB
② DOWNLOAD & RUN MALWARE
shell access → download payload via certutil/bitsadmin → execute → full backdoor
③ LATERAL MOVEMENT
SQL Server often runs as SYSTEM → pivot to domain, steal credentials, move laterally
④ PERSISTENCE VIA SCHEDULED TASKS
OS shell → create scheduled tasks, registry run keys, or new local admin accounts
xp_cmdshell = SQL query → OS shell (SYSTEM level)
disabled by default. re-enabled by sysadmin in 2 SQL
statements. SQL Server often runs as NT AUTHORITY\SYSTEM.

HOW ATTACKERS GET IN — THE SA ACCOUNT
ACCESS VECTORS SA ACCOUNT
▸ the 'sa' account — SQL Server's built-in admin
sa = System Administrator
built-in SQL authentication account · full sysadmin role.
when SQL auth is enabled, 'sa' is always present.

commonly found in the wild with:
• blank password (empty string)
• password = 'sa'
• password = the company name
• password from leaked breach database
▸ typical attack chain (concept, not steps)
1
port scan finds 1433 open externally → SQL Server exposed
2
attempt sa with blank/common passwords → login succeeds
3
check xp_cmdshell status → disabled → re-enable via sp_configure
4
execute OS commands as NT AUTHORITY\SYSTEM → full server control
5
establish persistence · move laterally to AD domain
DETECTION OPPORTUNITY
sp_configure changes are logged in SQL Server Error Log.
xp_cmdshell execution fires Event ID 15457 in Windows Event Log.
sa login from external IP should alert immediately — never normal.
sa + blank password = instant sysadmin over SQL auth
1433 exposed + sa account + weak password = full OS
compromise in minutes. still found in production.

HARDENING — 6 CONTROLS THAT MATTER
HARDENING CHECKLIST
① DISABLE xp_cmdshell — PERMANENTLY
disable via sp_configure and lock with policy.
use DDL trigger to alert + revert if re-enabled.
no legitimate app should need xp_cmdshell in production.
# disable and lock xp_cmdshell
EXEC sp_configure 'xp_cmdshell', 0; RECONFIGURE;
EXEC sp_configure 'show advanced options', 0; RECONFIGURE;
② WINDOWS AUTH ONLY — DISABLE SQL AUTH
SQL Auth mode allows sa and local SQL accounts.
Windows Auth (Kerberos) ties to AD — no sa, no SQL passwords.
set server authentication mode to "Windows Authentication Mode".
③ FIREWALL: NEVER EXPOSE 1433 EXTERNALLY
1433 should only be reachable from app server subnets.
firewall rule: allow 1433 only from 10.x.x.x/app-tier VLAN.
use SQL Server Browser service only on internal networks.
# Windows Firewall — block 1433 inbound from internet
netsh advfirewall firewall add rule name="Block SQL 1433"
protocol=TCP localport=1433 action=block dir=in
remoteip=0.0.0.0/0
④ RENAME / DISABLE THE SA ACCOUNT
if SQL Auth is required, disable 'sa' and create a named account.
rename sa to an obscure name — stops automated tooling.
enforce strong password policy on all SQL logins.
⑤ LEAST PRIVILEGE SERVICE ACCOUNT
SQL Server runs as SYSTEM by default → total OS access on compromise.
use a dedicated low-privilege domain service account.
grant only: logon as service, access to SQL data directories.
⑥ ENABLE SQL SERVER AUDIT TO SIEM
audit: successful/failed logins, sp_configure changes, DDL events.
ship to SIEM. alert on: sa login, xp_cmdshell enable, bulk export.
retention: 90 days minimum for incident response.
disable xp_cmdshell + Windows Auth + firewall 1433
these 3 controls eliminate 95% of MSSQL attack surface.
least-priv service account contains the blast radius.
