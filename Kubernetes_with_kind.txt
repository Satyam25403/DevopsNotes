When you run docker ps, you're seeing a container like:kindest/node
This is Kind's bootstrap container, not a Kubernetes pod. It's the actual Docker container that simulates a Kubernetes node — a whole node, including kubelet, container runtime, etc. Think of it as the VM that runs Kubernetes, not a pod inside Kubernetes.
- The kindest/node container is outside Kubernetes — it hosts the cluster. So Kubernetes doesn’t “see” it as a pod.
- Docker’s kindest/node container is the stage and the lighting — it enables the show to happen.
- Kubernetes pods are the actors performing scenes. When the stage is built, there are no actors until you cast them — that is, deploy pods.

kubectl scale deployment <deploymentname> --replicas=3

edit a deployment:
kubectl edit deployment <deploymentname> => thereafter u can make desired changes to the yaml it displays and as soon as we save...changes will be applied

what field does what? need a quick check?(a reference)

kubectl rollout history deployment

rollback the changes(undo the rollout):
kubectl rollout undo deployment <deploymentname>

### *1. Why Port-Forward is Needed in Kind*

* In Kind, each Kubernetes node is just a *Docker container* running on a private Docker network (e.g., 172.18.0.x).
* NodePorts (e.g., 30080) are exposed *inside that node container*, not on your host (localhost) by default.
* Unless you configure extraPortMappings in your Kind cluster config, your host can’t directly access NodePorts.

---

### *2. Port-Forward for ClusterIP*

* *ClusterIP Services* are internal-only — they have no NodePort or external IP.
* To reach them from your host, you must always do:

kubectl port-forward service/<name> 8080:80

* This tunnels traffic *through the Kubernetes API server* to the Pod(s):
Host (localhost:8080) 
   → API Server 
      → kube-proxy 
         → ClusterIP (10.x.x.x:80)
            → Pod IP (10.244.x.x:targetPort)
* *No direct Pod or node access*; everything is proxied.

---

### *3. Port-Forward for NodePort*

* Normally, NodePort makes a Service reachable via NodeIP:NodePort.
* In Kind, NodeIP is the *container’s IP* (like 172.18.0.2), not localhost.
  If you don’t map ports to the host, you can’t directly curl it.
* Using port-forward here:

bash
kubectl port-forward service/<name> 8080:80


* Even though it’s a NodePort, this still *bypasses NodePort* and just forwards like ClusterIP.

Traffic flow is the same as ClusterIP because port-forward:

* Does not care whether the Service is NodePort, ClusterIP, or LoadBalancer.
* Always tunnels via the API server.

---

### *Key Behaviour Difference*

* *ClusterIP: Always internal; port-forward is the *only way without reconfiguring Kind.
* *NodePort*: Meant to be accessible via NodeIP:NodePort, but in Kind you can’t reach it from the host unless:
	* You use the *node container IP* (not localhost), or
	* Add extraPortMappings to make localhost:30080 work, or
	* Skip NodePort entirely and just port-forward (which is simpler).

---

### *Why You Might Use NodePort in Kind Anyway*

* If you configure extraPortMappings when creating your Kind cluster, NodePort can work like Minikube (localhost:30080) without port-forward.
* Otherwise, NodePort behaves like ClusterIP because port-forward bypasses the NodePort mechanism.

=================================================CONFIG MAP============================================================

Implementing environmental variables more effectively: The kubernetes way
why we need? let us say we have 100s of env vars and let they are to be shared accross different manifests ex: app-deployment, frontend-deployment, backend-deployment

using env vars we need to specify them in all the deployment yamls/manifests=>better way would be
create one kubernetes configmap object containing all the env vars and =>map it with multiple deployments ...app-deployment,backend-deployment etc.
u can expose it to container as well in addition to mapping with deployment manifests

create config-map using command:
kubectl create configmap(or)cm --from-literal=FIRST_NAME=piyush --from-literal=LAST_NAME=sachdeva
kubectl get configmap/cm
kubectl describe configmap <configmapname>        =>shows the env vars


using manifest:
kubectl create configmap(or)cm --from-literal=FIRST_NAME=piyush --from-literal=LAST_NAME=sachdeva
--dry-run=client -o yaml > cm.yaml
cm.yaml=>
apiVersion: v1
data:
  FIRST_NAME: piyush
  LAST_NAME: sachdeva
Kind: configmap
metadata:
  creationTimestamp: null
  name: sample-cm1

we provide the reference of this configmap inside the deployment manifest

there is a deployment.yaml:
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: null
  labels:
    app: nginxdeploy
  name: nginxdeploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginxdeploy
  strategy: {}
  template:
    metadata:
      creationTimestamp: null
      labels:
        app: nginxdeploy
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          env:
          - name: FIRST_NAME
            valueFrom:
              configMapKeyRef:
                name: sample-cm1
                key: FIRST_NAME
          - name: LAST_NAME
            valueFrom:
              configMapKeyRef:
                name: sample-cm1
                key: LAST_NAME
          - name: SERVER_NAME
            valueFrom:
              configMapKeyRef:
                name: sample-cm2
                key: SERVER_NAME
          ports:
          - containerPort: 3000

NOTE: This strategy makes shared environment variables easily manageable across multiple deployment manifests.
Instead of hardcoding values in each manifest, simply reference the required keys from relevant ConfigMaps.
This centralizes management and boosts reusability.


NOTE: you can map env variables from different configmaps inside same deployment manifest as shown in above example
we took vars from sample-cm1 and sample-cm2
