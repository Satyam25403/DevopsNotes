## What is a Secrets Engine

**A Secrets Engine is a plugin that stores, generates, or transforms data — mounted at a specific path.**

**Visual:**
```
┌────────────────────────────────────────────────┐
│  Vault Server                                       │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────┐│
│  │ secret/          │  │ database/        │  │ transit/    ││
│  │ (KV engine)         │  │ (Database engine)  │  │ (Transit)  ││
│  └──────────────┘  └──────────────┘  └──────────┘│
└────────────────────────────────────────────────┘

Each engine is mounted at a path, and behaves completely
differently depending on its type — KV just stores what you
give it, Database actively creates new DB users on demand,
Transit never stores anything, it just encrypts/decrypts.
```

```bash
# List all enabled secrets engines
vault secrets list
```

## KV Secrets Engine (Static Secrets)

**The simplest engine — a secure, versioned key-value store. Good for API keys, config values, credentials that aren't dynamically generated by Vault itself.**

```bash
vault secrets enable -path=secret kv-v2
```

**Writing and reading:**
```bash
vault kv put secret/myapp/db username="admin" password="s3cr3tPass"
vault kv get secret/myapp/db
vault kv get -field=password secret/myapp/db
```

**Visual:**
```
Retrieving just one field (useful in scripts):
vault kv get -field=password secret/myapp/db
→ s3cr3tPass

Without -field, you get the FULL object (all keys),
which then needs separate parsing (e.g. with jq) in scripts:

vault kv get -format=json secret/myapp/db | jq -r '.data.data.password'
```

**Deleting and destroying:**
```bash
vault kv delete secret/myapp/db      # soft delete (recoverable, versioned)
vault kv destroy -versions=1 secret/myapp/db   # permanent, unrecoverable
```

## Versioning in KV v2

**Visual:**
```
Version History for secret/myapp/db:
┌─────────┬────────────────────────┬──────────────┐
│ Version   │ Data                      │ Status          │
├─────────┼────────────────────────┼──────────────┤
│ v1         │ password: "oldPass123"      │ deleted (soft)   │
│ v2         │ password: "s3cr3tPass"       │ current            │
│ v3         │ password: "rotatedPass456"    │ (future write)      │
└─────────┴────────────────────────┴──────────────┘

Get a specific old version:
vault kv get -version=1 secret/myapp/db

Roll back to a previous version:
vault kv rollback -version=1 secret/myapp/db
```

**Why versioning matters:** if a bad automated rotation writes a broken password, you can roll back instantly instead of manually reconstructing the previous value.

## Database Secrets Engine (Dynamic Secrets)

**Instead of storing a static password, Vault creates unique, temporary database users on demand.**

**Visual:**
```
Traditional Static Credential:
App config: db_password = "SharedPassword123"
   (same password used by every app instance, forever)

Vault Dynamic Credential:
App requests → Vault connects to DB as an ADMIN →
                creates a brand-new user →
                     ↓
        username: v-token-myrole-a1b2c3
        password: randomly-generated-xyz789
        TTL: 1 hour
                     ↓
        After 1 hour, Vault automatically DROPS this DB user
```

### Setup

```bash
vault secrets enable database

vault write database/config/postgres-db \
  plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@db-host:5432/mydb" \
  allowed_roles="readonly-role" \
  username="vault-admin" \
  password="admin-password-stored-once-here"

vault write database/roles/readonly-role \
  db_name=postgres-db \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" \
  max_ttl="24h"
```

### Requesting Credentials

```bash
vault read database/creds/readonly-role
```

**Visual:**
```
Terminal Output:
Key                Value
---                -----
lease_id           database/creds/readonly-role/abc123
lease_duration     1h
username           v-token-readonly-a1b2c3
password           A9x2-randomly-generated-Kp7

Each call to this command generates a DIFFERENT,
brand new database user — never reused.
```

**Visual — the lease/revocation lifecycle:**
```
Request credentials → DB user created → App uses it for up to 1h
                                              ↓
                                   Lease expires OR is renewed
                                              ↓
                              If expired/revoked: Vault runs the
                              REVOCATION statement, dropping the
                              DB user automatically
```

**Manually revoke early (e.g. app is being decommissioned):**
```bash
vault lease revoke database/creds/readonly-role/abc123
```

## Transit Secrets Engine (Encryption as a Service)

**Vault encrypts/decrypts your data, but NEVER stores it — the actual data always stays with your application.**

**Visual:**
```
Traditional Approach:
Every app implements its OWN encryption logic
→ inconsistent quality, key management scattered, error-prone

Transit Engine Approach:
┌──────────┐   plaintext    ┌──────────┐   ciphertext   ┌──────────┐
│  App         │ ─────────────→ │  Vault       │ ─────────────→│  App         │
│              │                 │  (encrypts,    │                │  (stores        │
│              │                 │   using a         │                │   ciphertext       │
│              │ ←───────────────│   named key,        │←───────────────│   in its own DB)     │
│              │   ciphertext     │   NEVER sees          │   ciphertext      │              │
└──────────┘                  │   or stores plaintext) │               └──────────┘
                                └──────────┘
Vault never stores the actual data — only performs the
encrypt/decrypt operation and returns the result.
```

### Setup

```bash
vault secrets enable transit
vault write -f transit/keys/customer-pii
```

**Encrypt:**
```bash
vault write transit/encrypt/customer-pii \
  plaintext=$(base64 <<< "John Doe's SSN: 123-45-6789")
```

**Visual:**
```
Terminal Output:
Key             Value
---             -----
ciphertext      vault:v1:8vZ9dGV...

Application stores THIS ciphertext in its own database —
Vault itself keeps zero copies of the plaintext or the ciphertext.
```

**Decrypt:**
```bash
vault write transit/decrypt/customer-pii \
  ciphertext="vault:v1:8vZ9dGV..."
```

**Visual — Key rotation without re-encrypting everything:**
```
vault write -f transit/keys/customer-pii/rotate
→ Creates key version 2

Old ciphertexts (encrypted with v1) still decrypt correctly
(Vault tracks which key version encrypted each ciphertext)

New encryptions automatically use v2

Optionally "rewrap" old ciphertexts to the newest key version
without ever exposing the plaintext to re-encrypt it:
vault write transit/rewrap/customer-pii ciphertext="vault:v1:..."
```

## Comparing the Three Engines

**Visual:**
```
┌──────────┬────────────────────┬───────────────────────────┐
│ Engine     │ What it does          │ Real Use Case                 │
├──────────┼────────────────────┼───────────────────────────┤
│ KV          │ Stores what you give it │ API keys, static config values  │
│ Database     │ Generates temp DB users  │ App database credentials,          │
│              │                          │ eliminating shared static passwords  │
│ Transit       │ Encrypts/decrypts,          │ Encrypting PII/sensitive fields       │
│              │ stores nothing              │ before storing in an app's own DB       │
└──────────┴────────────────────┴───────────────────────────┘
```

## Real-Life DevOps Use Case

**Scenario:** A DevOps engineer is hardening a customer-facing application handling payment data, and needs to address three separate secrets-related risks.

**What they implement:**
1. **API keys for third-party services** (payment gateway, email provider) → stored in the **KV engine**, versioned so a bad rotation can be rolled back instantly, and scoped via policy so only the `payments` team's AppRole can read them.
2. **Application's own database credentials** → migrated from a static password (that had been unchanged for 2 years) to the **Database secrets engine**, issuing 1-hour dynamic credentials per app instance. This immediately shrinks the blast radius if a credential ever leaks — it would already be expired within the hour.
3. **Customer PII (SSNs, card-adjacent data)** stored in the application's own database → encrypted using the **Transit engine** before being written to disk, so even a full database dump/backup leak doesn't expose readable PII. The app calls Vault's encrypt/decrypt API instead of implementing its own cryptography, avoiding common mistakes like weak algorithms or hardcoded encryption keys.
4. Sets up a **quarterly key rotation** for the Transit engine's `customer-pii` key, using `rewrap` to re-encrypt existing data under the newest key version without ever exposing plaintext during the process.

**Why this matters:** Combining all three engines addresses three genuinely different problems — static credential storage, dynamic/short-lived database access, and consistent encryption-as-a-service — each with the right tool rather than forcing one engine to do everything.
