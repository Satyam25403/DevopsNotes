💀 docker0 IS DNS-BLIND
The default bridge docker0 predates Docker's embedded DNS server. Name resolution was bolted on later — only for user-defined networks.
"Why does ping app-b fail?" — You're on the default bridge.
docker0 has no DNS. IPs only. User-defined networks fix this.

🔮 127.0.0.11 — EMBEDDED DNS

◈ HOW IT WORKS PROTOCOL

🔮 DOCKER INJECTS THE RESOLVER
Docker rewrites /etc/resolv.conf in every container on a user-defined network. The nameserver is always 127.0.0.11 — a loopback address that intercepts DNS queries before they leave the container.
WHAT 127.0.0.11 KNOWS:
→ Every container name on the same network
→ Every service name from docker-compose
→ All --network-alias values (multiple names)
✗ Containers on OTHER networks
✗ Containers on the default bridge
Every user-net container gets nameserver 127.0.0.11 auto-injected.
This resolver knows every container name — but only within the same network.

⚰ --link vs --network-alias
THE OLD WAY IS DEAD. LONG LIVE ALIASES.
⚰ DEPRECATED STOP USING
☠ --link (DEPRECATED since Docker 1.12)
docker run --link app-b:alias app-a
# What it did (badly):
→ injected env vars: APP_B_PORT_6379_TCP
→ added /etc/hosts entry for alias
✗ one-directional only
✗ breaks when container restarts
✗ does NOT work across networks
☠ DO NOT USE THIS
✓ --network-alias (multiple DNS names per container)
docker run -d \
--network mynet \
--name redis-primary \
--network-alias cache \
--network-alias db-cache \
redis
# Now reachable by 3 names:
ping redis-primary ← container name
ping cache ← alias 1
ping db-cache ← alias 2
💡 ALIAS USE CASE: BLUE/GREEN DEPLOYS
Point multiple containers at the same alias "api". DNS round-robins between them. Swap containers without changing any client config.
--link is deprecated. It's fragile, one-directional, and breaks on restart.
--network-alias gives a container multiple DNS names. Use it instead.
