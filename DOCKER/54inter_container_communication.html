# reach any container by its --name:
$ docker exec web curl http://api:3000 ✓
$ docker exec api psql postgres://db:5432 ✓
✓ THE RULE
Same user-defined network = container name is hostname. Port is the internal port, NOT the published one. No IPs needed. Compose does this automatically for every service.
Same network = container name resolves automatically via 127.0.0.11.
Use the internal port (3000, 5432) — not the published host port.

② SAME HOST · DIFF NETS
docker network connect — THE BRIDGE
SCENARIO 2 CROSS-NET
same host · two isolated networks · one bridging container
docker network connect
# API already on net-B with db
$ docker network connect net-A api
api now has TWO IP addresses ✓
# verify both networks attached:
$ docker inspect api --format \
'{{json .NetworkSettings.Networks}}'
{"net-A":{...}, "net-B":{...}} ← both!
💡 HOW IT WORKS
A container joined to two networks gets a separate IP on each. It can route traffic between them. This is how docker compose implements the API-as-gatekeeper pattern — frontend-net and backend-net with api on both.
docker network connect adds a second NIC + IP to a running container.
The gatekeeper container sees both networks. Others see only one.

③ MULTI-HOST · NO SWARM
HOST NET + CONSUL / ETCD SERVICE DISCOVERY
SCENARIO 3 ADVANCED
two separate hosts · external service registry
consul registration pattern
# on container start (entrypoint script)
curl -X PUT http://consul:8500/v1/agent/service/register \
-d '{"Name":"db","Address":"192.168.1.11","Port":5432}'
# app resolves db address at runtime:
DB_ADDR=$(curl consul:8500/v1/catalog/service/db \
| jq -r '.[0].ServiceAddress+":"+.[0].ServicePort')
→ DB_ADDR=192.168.1.11:5432 ← discovered!

④ MULTI-HOST · SWARM
OVERLAY NETWORK · AUTOMATIC DNS
SCENARIO 4 PRODUCTION
docker swarm · overlay network · VXLAN tunnels
docker swarm setup
$ docker swarm init # on manager node
$ docker swarm join --token ... nodeB
$ docker network create \
--driver overlay my-overlay
$ docker service create \
--network my-overlay --name api \
--replicas 2 my-api-image
# "api" resolves from ANY node ✓
◈ PATTERN DECISION GUIDE
① same net → container name (always start here)
② diff nets → docker network connect
③ multi-host, no Swarm → host net + Consul/etcd
④ multi-host, Swarm → overlay + service DNS
Swarm overlay = virtual L2 network across all hosts. DNS is automatic.
Service name resolves to a VIP. Swarm load-balances across all replicas.
