WHERE DID THOSE INSTRUCTIONS COME FROM?
THE ANSWER: ONBUILD
ONBUILD stores instructions inside a parent image. They do nothing when the parent is built. They fire automatically the moment any child image uses that parent as its FROM base.
ONBUILD instructions sleep inside the parent image.
They wake up the instant a child image runs FROM parent.

# Platform team writes this once
FROM node:20-alpine
WORKDIR /app
# These run NOW, in the parent build:
RUN apk add --no-cache curl
ENV NODE_ENV=production
# These are DEFERRED to child builds:
ONBUILD COPY package*.json ./
ONBUILD RUN npm ci --only=prod
ONBUILD COPY . .
CMD ["node","server.js"]

RULES & GOTCHAS
WHAT TO KNOW BEFORE YOU USE IT
GOTCHAS READ THIS
ONBUILD RULES
✓
FIRES ON DIRECT CHILDREN ONLY
ONBUILD does NOT chain. Grandchildren (FROM child-image) do not inherit grandparent's ONBUILD triggers.
✕
CANNOT ONBUILD an ONBUILD
Nesting ONBUILD inside ONBUILD is not allowed and will error at build time.
✕
NO FROM or MAINTAINER
FROM and MAINTAINER are not allowed as ONBUILD targets. Everything else (COPY, RUN, ENV, CMD…) is fair game.
⚠
INVISIBLE TO CHILD AUTHORS
Triggers are hidden from the child Dockerfile. Always document ONBUILD behaviour in the parent image's README.
✓ USE IT WHEN
Platform team building standardized base images.

Same build steps repeated across 10+ services.

Want to enforce conventions automatically.
✕ AVOID WHEN
Only 1–2 services use the base image.

Child teams need to understand what's happening.

Using Docker Compose or multi-stage builds instead.
★ ALWAYS INSPECT UNKNOWN BASE IMAGES
Before using a corporate base image, run docker inspect <image> | grep -A10 OnBuild to see what triggers are hiding inside.
ONBUILD only fires in direct children — not grandchildren. No chaining.
Always document ONBUILD triggers — they're invisible to child authors.
