start docker daemon:
sudo systemctl start docker         (or)
dockerd &               =>if systemctl not available(-  systemctl commands won’t work in most containers)
🔧 Prerequisites
- Make sure containerd is installed and running.
- You may need to install iptables, cgroup support, and other dependencies depending on your base image.

🧠 Alternative: Use Host Docker from Inside Container
If your goal is just to run Docker commands from inside the container, you can mount the host’s Docker socket:
docker run -v /var/run/docker.sock:/var/run/docker.sock -it ubuntu
This lets you use the host’s Docker daemon without needing to start one inside the container.


If your goal is to run Docker inside Docker, the recommended way is to use the official Docker-in-Docker image:
docker run --privileged --name dind-test -d docker:dind

What Are Dangling Images in Docker?
Dangling images are Docker images that:
Have no name (tag) → their repository and tag are <none>:<none>
Are not used by any container like these:
REPOSITORY          TAG       IMAGE ID       CREATED         SIZE
<none>              <none>    abc12345defg   10 minutes ago  300MB
They are intermediate build layers or outdated images left behind

Remove only dangling images:
docker image prune

Remove all unused images (dangling + unreferenced(nolonger being used by containers)):
docker image prune -a

RUN vs ENTRYPOINT vs CMD
RUN Purpose:
Used during the image build process.
Executes commands once when building the image (like installing packages or setting up files).
RUN apt update && apt install -y curl

CMD Purpose:
Provides default arguments or a command to run when the container starts.
Can be overridden when starting a container using docker run.
CMD ["python", "app.py"]
overridable while running=> docker run my-image python other_script.py

ENTRYPOINT Purpose:
Defines the main executable for the container.
Not easily overridden (unless using --entrypoint flag).
ENTRYPOINT ["python"]
CMD ["app.py"]




docker compose:making services run in single network
for ex:localhost for one doesnt mean same localhost for other

Why localhost doesn't mean the same across Docker containers?
Each Docker container has its own isolated network namespace — meaning each one is seperate instance...each is a seperate machine:
localhost (or 127.0.0.1) inside a container refers to itself — not the host or any other container.
So if Container A tries to call localhost:5000, it is calling itself, not Container B.
hence localhost for A and B both are seperate.

✅ How to Make Services Talk to Each Other
Use Docker Compose to run all services in the same custom network. Docker Compose does this by default.
docker-compose.yaml
version: '3.8'
services:
  frontend:
    image: yourname/frontend:latest
    environment:
      - BACKEND_URL=http://backend:5000/
    ports:
      - "3000:3000"
    depends_on:
      - backend
    networks:
      - app-network
  backend:
    image: yourname/backend:latest
    ports:
      - "5000:5000"
    networks:
      - app-network
  admin:
    image: yourname/admin:latest
    ports:
      - "4000:4000"
    networks:
      - app-network
networks:
  app-network: {}


💡 Then how do they communicate?
In this case:
The frontend can access the backend using:
http://backend:5000
Not:
❌ http://localhost:5000
Because:
backend is the service name, and Docker DNS will resolve it to the backend container's IP.

Example Use in Node.js Frontend
const response = await axios.post('http://backend:5000/submit', formData);

That works because:
Docker Compose puts both containers in the same network
backend is a valid hostname inside that network


Why Use Docker Compose?
Because it lets you:
Define all services, ports, networks, volumes, etc. in one YAML file
Launch everything with one command:

    docker compose up

Automatically create a shared network so containers can talk by service names
