LAYERS ARE IMMUTABLE
Once written, a layer never changes. Its SHA256 hash is its identity. Same hash = exact same bytes. Docker never rewrites a layer — it creates a new one.
TOP LAYER = MOST LIKELY TO CHANGE
Put your source code at the top. Base image and deps at the bottom — they change rarely so they stay cached. Rebuild hits only changed layers and above.
Layers stack bottom → top like a read-only filesystem.
A running container adds one thin writable layer on top. The image layers underneath are never touched — ever.

CACHE INVALIDATION RULE
Once any layer misses, all layers above it also miss — even if their files didn't change. The chain is broken. Order your Dockerfile so the most stable instructions come first.
A cache miss breaks the chain — every layer above rebuilds.
That's why COPY package.json → RUN npm install → COPY . . is the canonical pattern. Dependencies change rarely; source code changes constantly.

LAYER OPTIMISATION CHEATSHEET
✓
Chain RUN commands with &&
RUN apt update && apt install -y curl && rm -rf /var/lib/apt/lists/*
One layer. Cleanup included. Smaller image.
✓
Copy deps before source
COPY package*.json ./ → RUN npm install → COPY . .
npm install layer cached unless deps actually change.
✗
Don't put secrets in layers
Even if you RUN rm secret.txt later, the secret lives in the earlier layer forever. Use build args or runtime secrets.
✓
Use .dockerignore
Exclude node_modules, .git, *.log — keeps build context small and COPY . . layer from bloating.
docker history = X-ray for your image
Shows every layer, its size, and the instruction that created it. Use it to find which layer is bloating your image — then optimize the Dockerfile order.
