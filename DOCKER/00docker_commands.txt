Dangling images are Docker images that:
Have no name (tag) → their repository and tag are <none>:<none>
Are not used by any container like these:
REPOSITORY          TAG       IMAGE ID       CREATED         SIZE

RUN vs ENTRYPOINT vs CMD
RUN Purpose:
Used during the image build process.
Executes commands once when building the image (like installing packages or setting up files).
RUN apt update && apt install -y curl

CMD Purpose:
Provides default arguments or a command to run when the container starts.
Can be overridden when starting a container using docker run.
CMD ["python", "app.py"]
overridable while running=> docker run my-image python other_script.py

ENTRYPOINT Purpose:
Defines the main executable for the container.
Not easily overridden (unless using --entrypoint flag).
ENTRYPOINT ["python"]
CMD ["app.py"]

RUN builds the image, CMD runs the container

Image layers:  images are composed of layers. And each of these layers, once created, are immutable and those layers used to create the filesystem a container can use.
A layer is: A snapshot of filesystem changes(“What got added / removed / modified”)...layers live on the host machine not inside container.(something like: /var/lib/docker)

Example:
Ubuntu base → one layer
Install Node → another layer
Add app.js → another layer

Let’s look at a theoretical image:
The first layer adds basic commands and a package manager, such as apt.
The second layer installs a Python runtime and pip for dependency management.
The third layer copies in an application’s specific requirements.txt file.
The fourth layer installs that application’s specific dependencies.
The fifth layer copies in the actual source code of the application.

It allows layers to be reused between images. For example, imagine you wanted to create another Python application. Due to layering, you can leverage the same Python base
This will make builds faster and reduce the amount of storage and bandwidth required to distribute the images

A deeper dive into image layers: https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/

Dockerfile: text-based document that provides instructions to the image builder to create container images

FROM <image>                          :specifies the base image 
WORKDIR <path>                        :sets the working directory inside the image for subsequent COPY, RUN, CMD etc.
COPY <host-path> <image-path>         :copies files from the build context on the host into the image
RUN <command>                         :builder runs this command inside the container(this is different from the command that executes when we say >docker run...)
ENV <name> <value>                    :sets an environment variable at build time, which is also available at runtime(it exists in the image)
EXPOSE <port-number>                  :documents the port the application listens on(it wont expose until we do >docker run -p 8080:80)
USER <user-or-uid>                    :sets default user for all subsequent operations(so container dont run as root user)
CMD ["<command>", "<arg1>"]           :default command run when the container starts.(when we use >docker run <image>)

Production ready images have: max build cache, fast, secure, run as non-root and use multi-stage builds

You can actually view the history (or how the image was created) by using :
>docker image history <imagename>

Build cache(faster builds->optimized images):
Docker executes each instruction in your Dockerfile, creating a layer for each command and in the order specified.
Docker checks whether it can reuse the instruction from a previous build. If it finds that you've already executed a similar instruction before, it doesn't need to redo it. 
it’ll use the cached result so that builds becomes faster and more efficient

If one layer changes → that layer and everything after it is rebuilt.
ex:
If you change: RUN apt install -y nodejs
to:            RUN apt install -y nodejs npm
Docker invalidates that layer, Command is re-run, New layer is created...even small change=cache miss

Once a layer is invalidated,
Layer 1  ✔ cached
Layer 2  ❌ changed
Layer 3  ❌ rebuilt
Layer 4  ❌ rebuilt
Docker cannot reuse later layers, because: They depend on filesystem state from earlier layers hence
all subsequent layers are rebuilt to maintain consistency.

Bad dockerfile:
COPY . .
RUN npm install
Any code change → npm install reruns 😭

Good dockerfile(cache friendly):
COPY package.json package-lock.json ./
RUN npm install
COPY . .
even if Code changes → npm install cached

1.Build cache is invalidated when there are changes in a RUN instruction or in files copied using COPY or ADD
2.What does NOT invalidate cache? (important!)
❌ Container runtime changes
❌ CMD execution
❌ Logs
❌ Environment at docker run time
Only build-time inputs matter.

practical example case demonstrating importance of build caches: (bottom of page) https://docs.docker.com/get-started/docker-concepts/building-images/using-the-build-cache/

Multi-stage builds: In traditional builds, all build instructions are executed in sequence and in single build container(creating bulky images)
Multi-stage builds introduce multiple stages in your Dockerfile, each with a specific purpose. we can think of it like the ability to run different parts of a build
in multiple different environments, concurrently. By separating the build environment from the final runtime environment, we can significantly reduce the image size and attack surface.

Multi-stage builds are recommended for all types of applications:
1.For interpreted languages: JavaScript or Ruby or Python, you can build and minify your code in one stage, and copy the production-ready files to a smaller runtime image.
2.For compiled languages, like C or Go or Rust, multi-stage builds let you compile in one stage and copy the compiled binaries into a final runtime image. 
No need to bundle the entire compiler in your final image.

Example of muilt-stage build:
# Stage 1: Build Environment
FROM builder-image AS build-stage 
# Install build tools (e.g., Maven, Gradle)
# Copy source code
# Build commands (e.g., compile, package)

# Stage 2: Runtime environment
FROM runtime-image AS final-stage  
#  Copy application artifacts from the build stage (e.g., JAR file)
COPY --from=build-stage /path/in/build/stage /path/to/place/in/final/stage
# Define runtime configuration (e.g., CMD, ENTRYPOINT) 

🔹 Copy only what is needed
COPY --from=build-stage /path/in/build/stage /path/in/final/stage
Copies only the built output
Leaves behind: Source code, Compilers, Build tools

This Dockerfile uses two stages:
1.Build-stage:
Uses a heavy image
Contains: Build tools (Maven, Gradle, compilers)
includes commands to install build tools, copy source code, and execute build commands.
Purpose:  Compile / build the application
Output:   Final artifact (e.g., .jar, .exe, dist/ folder)
📌 This stage is not shipped to production

2.Final-stage:
Uses a lightweight image
No build tools
Only what is needed to run the app. It copies the compiled artifacts (a JAR file, for example) from the build stage. 
Finally, it defines the runtime configuration (using CMD or ENTRYPOINT) for starting your application.

Real-world example:
Stage 1: Java + Maven → build app.jar
Stage 2: Java only → run app.jar

example:
# -------- Stage 1: Build stage --------
FROM node:20 AS build
WORKDIR /app
# Copy dependency files first (better caching)
COPY package*.json ./
# Install all dependencies (including dev)
RUN npm install
# Copy source code
COPY . .
# Build the app (for React / TS / Nest etc.)
RUN npm run build

# -------- Stage 2: Runtime stage --------
FROM node:20-slim AS runtime
WORKDIR /app
# Copy only built output and production deps
COPY --from=build /app/dist ./dist
COPY --from=build /app/package*.json ./
# Install only production dependencies
RUN npm install --omit=dev
# App runs on this port
EXPOSE 3000
# Run the app
CMD ["node", "dist/index.js"]

Stage 1 – Build
Uses full Node image
Installs all dependencies
Builds the application
Produces output (e.g. dist/)

🔹 Stage 2 – Run
Uses lightweight Node image
Copies only:
built files
production dependencies
No source code
No dev tools

With multi-stage builds, a Docker build uses one base image for compilation, packaging, and unit tests and then a separate image for the application runtime.
As a result, the final image is smaller in size since it doesn’t contain any development or debugging tools.

With Docker Compose, you can define all of your containers and their configurations in a single YAML file.
docker compose:making services run with minimal setup and cleanup effort

localhost for one doesnt mean same localhost for other
Why localhost doesn't mean the same across Docker containers?
(incase u dockerized a frontend(5173) and backend(3000) and frontend needs to make api call, it can't simply call on localhost:8000 while it will work when u dont use docker to run the project)
if your frontend container tries http://localhost:3000, it’s looking for a backend process inside the same container, which doesn’t exist.
Each Docker container has its own isolated network namespace — meaning each one is seperate instance...each is a seperate machine:
localhost (or 127.0.0.1) inside a container refers to itself — not the host or any other container.
So if Container A tries to call localhost:5000, it is calling itself, not Container B.
hence localhost for A and B both are seperate.

💡 Then how do they communicate?
In this case:
The frontend can access the backend using:
http://backend:5000
Not:
❌ http://localhost:5000
Because:
backend is the service name, and Docker DNS will resolve it to the backend container's IP.

Example Use in Node.js Frontend
const response = await axios.post('http://backend:5000/submit', formData);

That works because:
Docker Compose puts both containers in the same network
backend is a valid hostname inside that network

✅ How to Make Services Talk to Each Other: use names that docker DNS resolves to(service discovery)
Use Docker Compose to run all services in the same custom network. Docker Compose does this by default.
docker-compose.yaml
version: '3.8'
services:
  frontend:
    image: yourname/frontend:latest
    environment:
      - BACKEND_URL=http://backend:5000/
    ports:
      - "3000:3000"
    depends_on:
      - backend
    networks:
      - app-network
  backend:
    image: yourname/backend:latest
    ports:
      - "5000:5000"
    networks:
      - app-network
  admin:
    image: yourname/admin:latest
    ports:
      - "4000:4000"
    networks:
      - app-network
networks:
  app-network: {}

A Dockerfile provides instructions to build a container image while a Compose file defines your running containers. 
Quite often, a Compose file references a Dockerfile to build an image to use for a particular service.

Why Use Docker Compose?
Because it lets you:
Define all services, ports, networks, volumes, etc. in one YAML file

Launch everything with one command:
>docker compose up

Automatically creates a shared network so containers can talk by service names

To shut down all containers at once that were started by docker compose:
>docker compose down

New dev workflow 😍(file sync+auto rebuild)
>docker compose watch

Docker:
Watches source files
Syncs only what changed
Restarts container if required
Rebuilds image if Dockerfile changes

Example: compose.yaml
services:
  web:
    build: .
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src

        - action: rebuild
          path: package.json
Run:
docker compose watch
What happens:
| Change                | Action              |
| --------------------- | ------------------- |
| Edit `src/app.js`     | Sync into container |
| Change `package.json` | Rebuild image       |
| Change Dockerfile     | Rebuild             |
| No manual restart     | 🎉                  |

Actions supported in watch:
| Action         | Meaning                 |
| -------------- | ----------------------- |
| `sync`         | Copy files to container |
| `rebuild`      | Rebuild image           |
| `restart`      | Restart container       |
| `sync+restart` | Both                    |

✅ Use it when:
Developing Node / Python / Java apps
Want hot reload without bind mounts
Hate permission & performance issues
Using Docker Compose v2+

❌ Don’t use when:
Production
Simple one-off containers
Already using in-container watchers (nodemon, uvicorn)

tagging images:
[HOST[:PORT_NUMBER]/]PATH[:TAG]

HOST: The optional registry hostname where the image is located. If not specified, Docker's public registry at docker.io is default.
PORT_NUMBER: The registry port number if a hostname is provided
PATH: The path of the image, consisting of slash-separated components. For Docker Hub, the format follows [NAMESPACE]/REPOSITORY, where namespace is either a user's or organization's name. 
If no namespace is specified, library is used, which is the namespace for Docker Official Images.
TAG: A custom, human-readable identifier that's typically used to identify different versions or variants.'latest' is used by default.

examples:
nginx, equivalent to docker.io/library/nginx:latestst
docker/welcome-to-docker, equivalent to docker.io/docker/welcome-to-docker:latest
ghcr.io/dockersamples/example-voting-app-vote:pr-311: an image from the GitHub Container Registry, dockersamples namespace, example-voting-app-vote image repository, pr-311 tag
