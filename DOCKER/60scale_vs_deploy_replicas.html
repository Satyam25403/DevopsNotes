DOCKER COMPOSE SCALING DEEP DIVE
STEP 1 — THE --SCALE FLAG COMPOSE V1
THE ORIGINAL WAY TO SCALE
In Compose v1, you'd pass --scale at runtime to spin up N containers for a service.
bash
$ docker-compose up --scale web=3
Creating project_web_1 ... done
Creating project_web_2 ... done
Creating project_web_3 ... done
⚠ web replicated 3x → 3 containers running
⚠ DEPRECATED IN COMPOSE V2
docker compose up --scale still works but is considered a runtime override — not declarative config. Compose V2 prefers deploy.replicas in the YAML.
--scale overrides at runtime — not stored in docker-compose.yml.
Great for testing. Bad for reproducible infra.

THE CHEAT SHEET
SCALE vs REPLICAS — WHEN TO USE WHAT
STEP 5 — SUMMARY REFERENCE
--scale FLAG (RUNTIME)
✓ Works with standalone docker compose
✓ Quick testing & dev environments
✗ Not declarative — not in YAML
✗ Lost on next docker compose up
DEPLOY.REPLICAS (YAML)
✓ Declarative — lives in docker-compose.yml
✓ Respected by Docker Swarm
✗ IGNORED by plain docker compose
✗ Confusing if you forget this rule
THE PORT RULE (CRITICAL)
✗ ports: "8080:80" + scale → CRASH
✓ ports: "80" (no host port) → WORKS
✓ Use a reverse proxy for :80 → replicas
QUICK DECISION GUIDE
Local dev / testing? → --scale
Docker Swarm prod? → deploy.replicas
Standalone compose prod? → --scale + no fixed ports
Any scaling setup? → reverse proxy!
deploy.replicas = for Swarm. --scale = for standalone.
Never scale with fixed host ports. Always use a reverse proxy.
