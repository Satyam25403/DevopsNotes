KEY DISTINCTION
ARG = build ingredient. ENV = container environment.
ARG evaporates when the image is built. ENV bakes into the image and is visible to every process that runs inside the container. Wrong choice = either broken config or a secret leak.

ARG — BUILD-TIME VARIABLE
SCOPE · --build-arg · DOCKER HISTORY LEAK
ARG BUILD-TIME
ARG SCOPE — AVAILABLE ONLY DURING BUILD
# Dockerfile: declare ARG with optional default
ARG NODE_ENV=development
ARG BUILD_VERSION
# Use during build
RUN echo "Building for $NODE_ENV"
# Pass value at build time:
docker build --build-arg NODE_ENV=production .
docker build --build-arg BUILD_VERSION=1.2.3 .
01
ARG is only available between the ARG instruction and the end of the build stage. If you try to use it in the container (docker exec, CMD, ENTRYPOINT), it's gone — undefined.
02
Pre-defined ARGs (no declaration needed): HTTP_PROXY, HTTPS_PROXY, FTP_PROXY, NO_PROXY, http_proxy, https_proxy. Also TARGETPLATFORM, BUILDPLATFORM for multi-arch builds.
ARG SCOPE
Available only from ARG instruction to end of build stage
ARG before FROM = global. ARG after FROM = scoped to that stage. In multi-stage, each stage needs its own ARG declaration even if the name is the same.

ENV — RUNTIME VARIABLE
PERSISTS INTO CONTAINER · -e FLAG · PROCESS ENV
ENV RUNTIME
ENV SCOPE — BAKED INTO IMAGE, VISIBLE AT RUNTIME
# set in Dockerfile
ENV NODE_ENV=production PORT=3000
# override at docker run
docker run -e NODE_ENV=development myapp
# or use an env file
docker run --env-file=.env.production myapp
# inspect what ENV vars are baked in:
docker inspect myapp --format '{{"{{"}}json .Config.Env{{"}}"}}'
✓
ENV is baked into the image as a layer. Every container started from that image inherits the value. But -e at docker run or environment: in compose overrides it at runtime.
!
ENV values are visible in docker inspect and in docker history. Never put secrets in ENV. Use Docker Secrets, Vault, or build-time --secret mount instead.
ENV PERSISTENCE
Baked into the image. Override with -e at runtime.
ENV is the right place for: PORT, NODE_ENV, DATABASE_URL structure, LOG_LEVEL. Never for passwords, API keys, or tokens — those are visible in docker inspect and history.

THE ARG→ENV PATTERN + SECRETS
HANDOFF PATTERN · HISTORY LEAK · WHAT TO USE INSTEAD
PATTERN + WARN ⚠ SECRETS
ARG→ENV Handoff Pattern — Dockerfile
# 1. Declare ARG (build-time input)
ARG NODE_ENV=production
ARG APP_VERSION
# 2. Bake into ENV (runtime output)
ENV NODE_ENV=$NODE_ENV
ENV APP_VERSION=$APP_VERSION
# Now: override at build, available at runtime
docker build --build-arg NODE_ENV=staging .
docker run myapp # NODE_ENV=staging in process
⚠ CRITICAL: ARG VALUES LEAK TO docker history
# BAD — this leaks to docker history!
ARG DB_PASSWORD=supersecret
RUN ./setup.sh
Running docker history shows:
IMAGE CREATED BY
a4f2... |1 DB_PASSWORD=supersecret /bin/sh -c ./setup.sh
↑ your secret is permanently visible to anyone with the image
✓ CORRECT: BuildKit --secret mount
# Dockerfile: mount secret, use in RUN, leaves no trace
RUN --mount=type=secret,id=db_password \
  DB_PASS=$(cat /run/secrets/db_password) ./setup.sh
# Build:
docker build --secret id=db_password,src=.db_password .
# Secret never appears in docker history ✓
⚠
ARG in docker history is permanent. Even if you overwrite the ARG in a later layer, the original value is in the layer cache. Anyone who pulls your image can run docker history and see it.
SECRETS RULE
Never put secrets in ARG or ENV. Use --secret.
ARG leaks in docker history. ENV leaks in docker inspect. For real secrets: BuildKit --secret (build-time), Docker Secrets (runtime), or external vaults (Vault, AWS Secrets Manager).
