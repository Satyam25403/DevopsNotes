STEP 2 — TAG STRATEGY PROTOCOL
① FEATURE BRANCH git push → open PR
$ docker build -t myapp:pr-123 .
$ docker push myapp:pr-123
# ephemeral — deleted when PR closes
② MERGE TO MAIN immutable forever
$ docker build -t myapp:sha-abc1234 .
$ docker push myapp:sha-abc1234
# pinned to this exact git commit
③ RELEASE DAY retag — no rebuild!
# promote existing image — no rebuild
$ docker tag myapp:sha-abc1234 myapp:1.2.0
$ docker tag myapp:sha-abc1234 myapp:latest
$ docker push myapp:1.2.0 myapp:latest

STEP 3 — DIGEST PROMOTION CORRECT
THE GOLDEN RULE
The binary that passed tests is the binary you deploy. Never rebuild. Use docker tag or registry promotion APIs to move the same image digest forward.
✓ CORRECT — promote the same digest
promotion script
# pull by digest — guaranteed same image
$ docker pull myapp@sha256:abc1234...
$ docker tag myapp:sha-abc1234 myapp:1.2.0
$ docker push myapp:1.2.0
✓ same bits, new alias
docker tag creates an alias — it does NOT copy or rebuild the image.
Build once, promote the digest. Same sha256 from dev to prod.

WHY PIN BY DIGEST?

⚠ ON USING :LATEST
Use :latest in dev/CI as a convenience pointer. Never reference it in production manifests — it's mutable and will silently change under you. Use semver or digest in prod.
