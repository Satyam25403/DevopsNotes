Data written to the container layer doesn't persist when the container is destroyed. This means that it can be difficult to get the data out of the container if another process needs it.
writable layer is unique per container. You can't easily extract the data from the writeable layer to the host, or to another container. Hence we use storage mounts

Docker supports these types of storage mounts:

1.Volume mounts: 
Volume data is stored on the filesystem on the host, but in order to interact with the data in the volume, you must mount the volume to a container
Docker creates & manages the directory
You don’t care where on host it lives

✅ Use case
Databases (MySQL, PostgreSQL)
App state
Production workloads

example:
docker volume create mydata

docker run -d \
  --name mysql-db \
  -v mydata:/var/lib/mysql \
  mysql:8

MySQL writes data to /var/lib/mysql inside container
Docker stores it somewhere like:
/var/lib/docker/volumes/mydata/_data

==================================================================================================================================================================================================

2.Bind mounts: 
create a direct link between a host system path and a container, allowing access to files or directories stored anywhere on the host.
both non-Docker processes on the host and container processes can modify the mounted files simultaneously. We control the exact location
Use bind mounts when you need to be able to access files from both the container and the host.

✅ Use case
Local development
Config files
Logs
Sharing source code
⚠️ Not ideal for production (host-dependent, security risk)

Example:
Let /home/satyam/app/index.html be host directory
run container:
docker run -it \
  -v /home/satyam/app:/usr/share/nginx/html \
  -p 8080:80 \
  nginx

🧪 Test
Edit index.html on host
Refresh browser → changes appear instantly

=============================================================================================================================================================================

3.tmpfs mounts: 
stores files directly in the host machine's RAM, ensuring the data is not written to disk. This storage is ephemeral: Destroyed on container stop/restart,
or when the host is rebooted. suitable for scenarios requiring temporary, in-memory storage, such as caching intermediate data, handling sensitive information like credentials,
or reducing disk I/O.

✅ Use case
Credentials
Session data
Temporary cache
Reduce disk I/O

Example:Temporary sensitive data:
docker run -it \
  --tmpfs /run/secrets \
  ubuntu
inside container:
echo "SECRET=12345" > /run/secrets/key.txt
Stop container → 💥 data gone

Example: High speed cache:
docker run -d \
  --tmpfs /cache:rw,size=64m \
  redis

===========================================================================================================================================================================================

4.Named pipes:
Used for communication between the Docker host and a container. Common use case is to run a third-party tool inside of a container and connect to the Docker Engine API using a named pipe.
Used mainly for inter-process communication. Common on Windows & Docker Engine API access

Example (Windows): Docker Engine API access
docker run -it `
  -v \\.\pipe\docker_engine:\\.\pipe\docker_engine `
  docker
Container can now talk to Docker daemon on host

Example (Linux – FIFO pipe)
Host:
mkfifo /tmp/my_pipe

Run container:
docker run -it \
  -v /tmp/my_pipe:/tmp/my_pipe \
  ubuntu

Host writes:
echo "hello" > /tmp/my_pipe

Container reads:
cat /tmp/my_pipe

✅ Use case
Docker CLI inside container
Debugging tools
IPC with host services
⚠️ Security sensitive — container can control host Docker

| Type       | Managed by Docker   | Persistent | Use case         |
| ---------- | ------------------  | ---------- | ---------------- |
| Volume     |  Yes                |  Yes       | Databases, prod  |
| Bind mount |  No                 |  Yes       | Dev, configs     |
| tmpfs      |  No                 |  No        | Secrets, cache   |
| Named pipe |  No                 | IPC only   | Host ↔ container |

Data persistance:
When a container is deleted, the file changes(creat.ions, updates and deletions) are also deleted.
Volumes are storage mechanism that provide ability to persist data beyond lifecycle of the container.
imagine it like a shortcut or symlink from inside of container to outside of container.

create volume:
>docker volume create <volumename>

mount onto container(in some location):
>docker ruun -d -p <HOST>:<CONTAINER-PORT> -v <volumename>:</directory/in/container> <image>
when container runs, all files it writes to the given directory in container will be saved in given volume(outside of container).
we can use same volume attach it to new container to same directory and see the data persists.

File-sharing:
Attaching same volume to multiple containers might help to gather data in central location.
Useful in cases like log-aggregation, data-pipelines or other event-driven applications.

Managing volumes:
Volumes have their own lifecycle beyond that of container and can grow quite large.
>docker volume -ls                  :list all volumes
>docker volume rm <vol-name-or-id>  :remove a volume(only removes if not attached to a container)
>docker volume prune                :remove all unattached volumes

Docker desktop allows us to view contents of a volume as well as ability to export, import, empty, delete and clone volumes.
NOTE: before removing volumes, stop and remove the container it is attached to

Sharing local files with docker:
Containers run in isolation and cannot access host files by default.To allow containers persist data:(use volumes)
and to share files with host system:(use bind mounts)

Volumes:
Managed by docker
Stored in dockers internal location
best for persistent data(databases, app data) is safer and portable
Survives container removal

Bind Mounts:
Directly map host directories/files into a container.
changes reflect instantly on host as well as container.
Best for development, config files, source code (real-time file sharing)

>docker run -v <HOST/PATH>:<CONTAINER/PATH> <image>                                       :creates host directory if missing
>docker run --mount type=bind,source=</HOST/PATH>,target=</CONTAINER/PATH> <image>        :safer, recommended and production use...file changes sync instantly with bind mounts
>docker run -v <HOST/PATH>:<CONTAINER/PATH>:ro <image>                                    :(ro)read-only mounts protect accidental host file changes(:rw read-write is default permission)

an example on page(at bottom): https://docs.docker.com/get-started/docker-concepts/running-containers/sharing-local-files/
