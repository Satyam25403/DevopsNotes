=========================================SECURITY GROUPS=======================================================
security group: analogous to a fire wall......it has a bunch of rules for traffic=> inbound/outbound rules
for your EC2 instances (and other resources). It controls inbound and outbound traffic based on a set of rules you define.

🔐 Security Group Basics
- Inbound Rules: Define what traffic is allowed into your instance (e.g., allow HTTP on port 80, SSH on port 22).
- Outbound Rules: Define what traffic your instance can send out (e.g., allow all traffic to the internet).
- Stateful(by default): If you allow inbound traffic from an IP on a port, the response traffic is automatically allowed back out — no need to define outbound rules for it.

🧱 Analogy: Like a Firewall with a Guest List
Imagine your EC2 instance is a private club:
- The Security Group is the bouncer.
- The rules are the guest list — who can enter, and through which door (port).
- If someone’s not on the list, they’re not getting in.

You can attach multiple security groups to an instance, and the rules are aggregated — meaning if any group allows the traffic, it’s permitted.

An important point to note:
Security Groups do control inbound traffic, but only in a permissive way. That means:
• 	You can restrict access by not allowing certain traffic.
• 	But you cannot explicitly deny traffic — there's no “deny” rule like you'd find in traditional firewalls or Network ACLs.

🔍 So what's really happening?
• 	If none of the attached security groups allow a specific inbound traffic type (say, TCP on port 3306), then that traffic is blocked by default.
• 	If any attached security group allows it, then it’s allowed, regardless of what other groups say.
So yes — you’re controlling inbound traffic, but only by omission. 
You’re saying “only these guests are allowed,” not “these guests are banned.”

Imagine your EC2 instance is a club with multiple bouncers (security groups). Each bouncer has a guest list:
• 	If any bouncer says “this person can come in,” they’re let in.
• 	If none of the bouncers recognize the guest, they’re turned away.
• 	But no bouncer ever says “this person is banned” — they just stay silent.

NOTE:
If you want explicit deny rules, that’s where Network ACLs come in

When multiple services are hosted on the same IP but differentiated by subdomains 
(like app.altair.com, blog.altair.com, etc.), and users access them via standard ports 
(usually 80 for HTTP or 443 for HTTPS), you need a smart traffic director to route requests correctly. 
That’s where reverse proxies and Ingress controllers come into play.

- Browser: Sends a request to app.altair.com
- DNS: Resolves app.altair.com to a shared IP (e.g., 203.0.113.10)
- Server: Receives the request on port 80
- Problem: All requests hit the same IP and port — how do we know which app to serve?

🧠 Solution: Host-Based Routing
You need a component that:
- Listens on port 80 (or 443)
- Reads the Host header from the HTTP request
- Routes traffic to the correct backend service based on that header

Ingress:kubernetes deployments

====================================== SSL(secure socket layer)/TLS(Transport layer security)===================================================
used to secure website over https connections
Because when we dont use https and use http we send packets accross the internet and anyone who is sniffing, can capture them
Exactly — that’s the core reason HTTPS exists: to protect data in transit from prying eyes.

https: port 443  http: port 80

🔐 Why HTTPS Matters
When you use HTTP, your browser sends requests and receives responses in plain text. That means:
- Login credentials
- Personal data
- Session cookies
- Even search queries
can be intercepted by anyone with access to the network — like someone on public Wi-Fi or a compromised router.
This is called packet sniffing, and tools like Wireshark make it surprisingly easy.

🛡️ What HTTPS Does
HTTPS (HyperText Transfer Protocol Secure) wraps HTTP inside TLS encryption, so:
- All data is encrypted before it leaves your browser
- Only the intended server can decrypt it
- It also authenticates the server using a certificate, so you know you're talking to the real site

==================================Running server even upon ec2 ssh disconnect=========================================
Using nohup with & on an EC2 instance is a classic way to run long-lived processes in the background 
especially when you want them to survive even after you disconnect your SSH session.

🛠 What Does It Do?
nohup your-command & 
ex: nohup python3 app.py &
logs are in => nohup.out

- nohup: Prevents the process from being terminated when the terminal session ends (ignores the SIGHUP signal(ctrl+c or exit)).
- &: Runs the command in the background so your terminal is free for other tasks.

✅ Example: Run a Python Script on EC2
nohup python3 my_script.py > output.log 2>&1 &


- > output.log: Redirects standard output to a log file.
- 2>&1: Redirects standard error to the same log file.
- &: Sends the process to the background.
Now you can safely close your SSH session or just do ctrl+c to stop the process, the script will keep running.

🔍 Check If It's Running
ps aux | grep my_script.py

Or check the output:
tail -f output.log

🧠 Pro Tip: Use setsid for Extra Isolation
If you find nohup alone isn't enough (some EC2 setups still kill the process), try:
setsid nohup python3 my_script.py > output.log 2>&1 &

This starts the process in a new session, giving it even more independence from your terminal.

---
To stop a background process that was started with nohup and is still running after you've disconnected from your SSH session, you’ll need to:

🛑 Step 1: Reconnect to Your EC2 Instance...if u just pressed ctl+c to just stop the process and still logged in u can skip this step
ssh username@your-ec2-ip

🔍 Step 2: Find the Process
You can locate it using:
ps aux | grep <your-command-or-script-name>

Or if you know it was started with nohup, try:
ps aux | grep nohup           (or)
sudo lsof -i -P -n | grep LISTEN
This will show you the PID (Process ID) of the running job.

🧨 Step 3: Kill the Process
Once you have the PID, stop it with:
kill <PID>

If it refuses to die:
kill -9 <PID>               {9:send a SIGKILL signal, strongest and most non-negotiable}
15:SIGTERM(graceful termination), 2:SIGINT(interrupt like ctrl+c), 9:SIGKILL(force kill)
🧠 Why Use It?
- When a process ignores softer signals like SIGTERM (kill -15) or Ctrl+C
- When it's stuck, unresponsive, or zombie-like
- When you need it gone now, regardless of consequences
⚠️ Caution
Because SIGKILL doesn’t allow the process to clean up:
- It might leave behind temporary files, locks, or unfinished task


🧼 Optional: Clean Up the nohup.out File
If you want to remove the output log:
rm nohup.out

🧠 Pro Tip: Use pgrep for Simplicity
If your script is called my_script.py, you can do:
pgrep -f my_script.py

Then:
kill $(pgrep -f my_script.py)
