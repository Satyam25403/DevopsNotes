When you run docker ps, you're seeing a container like:kindest/node
This is Kind's bootstrap container, not a Kubernetes pod. It's the actual Docker container that simulates a Kubernetes node — a whole node, including kubelet, container runtime, etc. Think of it as the VM that runs Kubernetes, not a pod inside Kubernetes.
- The kindest/node container is outside Kubernetes — it hosts the cluster. So Kubernetes doesn’t “see” it as a pod.
- Docker’s kindest/node container is the stage and the lighting — it enables the show to happen.
- Kubernetes pods are the actors performing scenes. When the stage is built, there are no actors until you cast them — that is, deploy pods.

### *1. Why Port-Forward is Needed in Kind*

* In Kind, each Kubernetes node is just a *Docker container* running on a private Docker network (e.g., 172.18.0.x).
* NodePorts (e.g., 30080) are exposed *inside that node container*, not on your host (localhost) by default.
* Unless you configure extraPortMappings in your Kind cluster config, your host can’t directly access NodePorts.

---

### *2. Port-Forward for ClusterIP*

* *ClusterIP Services* are internal-only — they have no NodePort or external IP.
* To reach them from your host, you must always do:

kubectl port-forward service/<name> 8080:80

* This tunnels traffic *through the Kubernetes API server* to the Pod(s):
Host (localhost:8080) 
   → API Server 
      → kube-proxy 
         → ClusterIP (10.x.x.x:80)
            → Pod IP (10.244.x.x:targetPort)
* *No direct Pod or node access*; everything is proxied.

---

### *3. Port-Forward for NodePort*

* Normally, NodePort makes a Service reachable via NodeIP:NodePort.
* In Kind, NodeIP is the *container’s IP* (like 172.18.0.2), not localhost.
  If you don’t map ports to the host, you can’t directly curl it.
* Using port-forward here:

bash
kubectl port-forward service/<name> 8080:80


* Even though it’s a NodePort, this still *bypasses NodePort* and just forwards like ClusterIP.

Traffic flow is the same as ClusterIP because port-forward:

* Does not care whether the Service is NodePort, ClusterIP, or LoadBalancer.
* Always tunnels via the API server.

---

### *Key Behaviour Difference*

* *ClusterIP: Always internal; port-forward is the *only way without reconfiguring Kind.
* *NodePort*: Meant to be accessible via NodeIP:NodePort, but in Kind you can’t reach it from the host unless:
	* You use the *node container IP* (not localhost), or
	* Add extraPortMappings to make localhost:30080 work, or
	* Skip NodePort entirely and just port-forward (which is simpler).

---

### *Why You Might Use NodePort in Kind Anyway*

* If you configure extraPortMappings when creating your Kind cluster, NodePort can work like Minikube (localhost:30080) without port-forward.
* Otherwise, NodePort behaves like ClusterIP because port-forward bypasses the NodePort mechanism.

=================================================CONFIG MAP============================================================

Implementing environmental variables more effectively: The kubernetes way
why we need? let us say we have 100s of env vars and let they are to be shared accross different manifests ex: app-deployment, frontend-deployment, backend-deployment

using env vars we need to specify them in all the deployment yamls/manifests=>better way would be
create one kubernetes configmap object containing all the env vars and =>map it with multiple deployments ...app-deployment,backend-deployment etc.
u can expose it to container as well in addition to mapping with deployment manifests

create config-map using command:
kubectl create configmap(or)cm --from-literal=FIRST_NAME=piyush --from-literal=LAST_NAME=sachdeva
kubectl get configmap/cm
kubectl describe configmap <configmapname>        =>shows the env vars


using manifest:
kubectl create configmap(or)cm --from-literal=FIRST_NAME=piyush --from-literal=LAST_NAME=sachdeva
--dry-run=client -o yaml > cm.yaml
cm.yaml=>
apiVersion: v1
data:
  FIRST_NAME: piyush
  LAST_NAME: sachdeva
Kind: configmap
metadata:
  creationTimestamp: null
  name: sample-cm1

we provide the reference of this configmap inside the deployment manifest

there is a deployment.yaml:
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: null
  labels:
    app: nginxdeploy
  name: nginxdeploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginxdeploy
  strategy: {}
  template:
    metadata:
      creationTimestamp: null
      labels:
        app: nginxdeploy
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          env:
          - name: FIRST_NAME
            valueFrom:
              configMapKeyRef:
                name: sample-cm1
                key: FIRST_NAME
          - name: LAST_NAME
            valueFrom:
              configMapKeyRef:
                name: sample-cm1
                key: LAST_NAME
          - name: SERVER_NAME                 =>name of env variable (this will be used in the code ex:as process.env.SERVER_NAME)
            valueFrom:
              configMapKeyRef:
                name: sample-cm2
                key: SERVER_NAME              =>key u specified in configmapyaml
          ports:
          - containerPort: 3000

==================================================RESOURCE: REQUESTS AND LIMITS=================================================================

OOM: Out of memory=>when memory utilization(ex:of a pod) crosses the available amount of memory(ex: in a node)
if not handled properly it can pre-empt the existing pods/workloads and kill the whole node...if it goes on aquiring the memory

in case of cpu:if crossed, cpu throttling may happen and can show performance issues

there is a pod.yaml
apiVersion: v1
Kind: Pod
metadata:
  name: stress-test
spec:
  containers:
  - image: polinux/stress
    name: stress-test
    command: ["stress"]
    resources:
      requests:
        cpu: "1"
        memory: "50Mi"                =>request this initially
      limits:
        cpu: "1"
        memory: "300Mi"               =>go upto this but not beyond
    args: ["--cpu","1","--vm","1","--vm-bytes","350M","--timeout","10s"]

NOTE: in yaml u specified requests and limits...but in command u r overriding the request to 350M>limit(300M)

kubectl apply -f pod.yaml

=========================================================HPA AND VPA======================================================================

Horizontal Pod Autoscaler=>object in k8s...based on some metrics and set thresholds...it scales the pods(existing pods are kept as is)
hence existing users(traffic) arent effected in HPA (not disruptive in nature=>hence widely used)
two types:when u scale based on workload(pods)=>HPA
          when u scale Infra(nodes)=>Cluster AutoScaler

Veritcal Pod AutoScaler=>upgrade to a bigger pod(more cpu and memory) and delete the prev pods=>traffic needs redirection(disruptive)
type: based on workloads(pods)=>VPA
      Infra(nodes)=>NodeAutoProvisioning(comes with managed cloud providers)

some scaling metrics: number of messages in kafka queue, number of concurrent connections to website/database which maynot be natively tracked=>all are events
Event based autoscaling:KEDA(3rd party tool)
Schedule based autoscaling:(like cron jobs)


Metrics Server:kubelet collects nodelevel metrics, pod metrics, container runtime etc and all those are passed to metrics server=>exposes them to API server with help of metrics API
some metrics: CPU, memory=>for scaling decisions, for realtime monitoring=>kubectl top

https://github.com/kubernetes-sigs/metrics-server
- download the metrics-server.yaml file from the deploy/kubernetes directory and apply to ur cluster

kubectl apply -f metrics-server.yaml

- Patch for insecure TLS (needed in local dev sometimes):
- If your cluster doesn’t have proper certs, you might need to update the deployment:
kubectl edit deployment metrics-server -n kube-system
- Then add this flag to the container args:
- --kubelet-insecure-tls

example deployment:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: metrics-server
  namespace: kube-system
spec:
  selector:
    matchLabels:
      k8s-app: metrics-server
  template:
    metadata:
      labels:
        k8s-app: metrics-server
    spec:
      containers:
      - name: metrics-server
        image: registry.k8s.io/metrics-server/metrics-server:v0.6.2
        args:
        - --cert-dir=/tmp
        - --secure-port=4443
        - --kubelet-preferred-address-types=InternalIP,ExternalIP,Hostname
        - --kubelet-insecure-tls
        ports:
        - containerPort: 4443
          name: https
          protocol: TCP

- --kubelet-insecure-tls: Skips TLS verification for Kubelet certificates. Useful in local clusters like Kind or Minikube where certs may not be signed by a trusted CA.
since it's a local dev environment, kubelets might use self-signed or missing certs.
- Make sure this deployment is applied in the kube-system namespace.
🔧 Why It Matters
If you apply the Metrics Server YAML without specifying a namespace, it might end up in the default namespace, which could cause issues:
- It won't connect correctly to the kubelet.
- You might not see metrics when using kubectl top.

kubectl apply -f metrics-server.yaml -n kube-system

- Restart the deployment if needed(delete and apply manually)/rollout(without downtime):
kubectl rollout restart deployment metrics-server -n kube-system
