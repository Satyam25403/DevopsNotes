what is kubernetes?
container orchestration(manage,create,delete,maintain,configure) tool for managing containers effeciently


kubernetes components:
🧠 Core Concepts (With Real-World Analogy) developers perspective:
| Pod => Smallest deployable unit, holds one or more containers => A shipping box containing items (containers) | 
| Node => A vm/machine in the cluster (has cpu/memory)=> A worker in a warehouse to run boxes (pods) | 
| Cluster => Collection of nodes => The entire warehouse system | 
| Deployment => Blueprint for managing pods(non stateful) => A plan saying “Keep 3 of these boxes running at all times” | 
| StatefulSet => Manages pods with persistent identity and storage(similar to deployment except for the persistance)
| Service => Exposes pods to the network => A receptionist routing requests to the right boxes | 
| Namespace => Logical partitioning => Like labeled rooms in the warehouse (dev, prod, test) | 
| ReplicaSet => Ensures a specified number of pod replicas are running
| DaemonSet => Ensures one pod per node (for monitoring/logging etc.)
| ConfigMap => Stores configuration data as key-value pairs
| Ingress => Manages external access to services (HTTP/HTTPS):single point of entry=>only single point of exposure...otherwise we would need to expose more and more prone to attack
| Volume => Persistent storage attached to pods(persistant volumes(pv),persistant volume claims(pvc))
| Scheduler => Assigns pods to nodes based on resource availability
| Controller Manager=> Oversees controllers like Deployments, ReplicaSets


k8s architecture:
-Master Node(atleast 1){it has components of worker nodes too}
  API server: Entry point for all commands and communication(allows us to use kubectl).- kubectl(client) sends HTTP requests (usually RESTful) to the Kubernetes API server.
The API server is the central gateway to the cluster—it validates, processes, and routes your commands.
  Scheduler: Assigns pods to nodes based on resource availability
  controller manager: Watches cluster state and triggers changes
  etcd: Key-value store for cluster state and config
-worker nodes(0 or more)
  kubelet: Talks to the container runtime and manages pods
  kube proxy: Handles networking,ips,ports and loadbalancing (routing requests)
  Container runtime: runs containers(CRI: for ex docker,containerd)


Minikube: allows to create kubernetes clusters locally but can be resource intensive(might slow down machine)
alternative can be kind but with lesser features
 Minikube
- Purpose: Spins up a full Kubernetes cluster locally.
- Pros:
- Supports multiple drivers (Docker, VirtualBox, Hyper-V, etc.)
- Includes Kubernetes Dashboard, Ingress, LoadBalancer emulation

ex: minikube start --nodes=3 -p dev-cluster
view all clusters/profiles => minikube profile list
switch between clusters/profiles => minikube profile <dev-cluster>
stop the cluster => minikube stop -p dev-cluster

- Ideal for CI/CD pipelines and quick testing

pods, deployments and services: an analogy
for example:
we have a backend Node.js server with APIs, DB logic, etc., and a frontend React app. 
Let’s say:
- Your backend is a containerized Node.js app.
- Your frontend is a React app built and served (e.g. via Nginx or Vite preview).
- You want them to talk to each other, scale if needed, and be resilient.
🧩 Backend
- Pod: Runs your Node.js container.
- Deployment: Ensures the backend pod is always running, maybe even horizontally scaled (replicas: 3).
- Service: Exposes the Node.js backend as backend-service so other pods (like React) can access it via DNS (http://backend-service:3000).
🧩 Frontend
- Pod: Runs React container (often served statically via Nginx).
- Deployment: Keeps your UI pods running and updates them safely.
- Service: Exposes the React frontend to external users (often type: LoadBalancer or NodePort).



PODS IN A NODE:
- Frontend and Backend are both containerized.
- Each Pod typically runs one container 
- You could have one pod for React.
- One pod for Node.js.
pod:(analogy=>One delivery shop or warehouse)

DEPLOYMENT:
scales and manages pods(a policy to be satisfied whatever may happen)
deployment:Says “Always keep 3 shops active”

NODES IN A CLUSTER:
- For horizontal scaling and separation of concerns, you'd usually:
- Create multiple frontend pods via a frontend deployment
- Create multiple backend pods via a backend deployment
All these pods run on available Nodes in your Cluster. Kubernetes decides placement.
node:(A city or town hosting your shops)
cluster:(Your entire delivery network)

SERVICES:
- You use Services to allow React to talk to Node via internal DNS names (e.g. http://backend-service:3000)
service:GPS routing system between stores

SETUP VISUALIZATION:
[Cluster]
   └── Node A (Host Machine)
       ├── Frontend Pod 1
       ├── Backend Pod 1
   └── Node B
       ├── Frontend Pod 2
       ├── Backend Pod 2
   └── Node C
       ├── Frontend Pod 3
       ├── Backend Pod 3
- If a Node gets overloaded, it moves pods to other Nodes.
- DNS inside Kubernetes lets the React app call http://backend-service:3000 without needing IPs.

Services:
- Frontend Service → exposes React to the outside world (users)
- Backend Service → internal connection for React to call APIs
it can control what to expose what not to
ex: Frontend exposed publicly, backend exposed only internally to frontend and not to outside internet or users

NAMESPACES:
💯 Spot on! That’s a brilliant way to think about namespaces—they let you parallelize production lines for 
graceful updates, experiments, or migrations with minimal risk. Here’s how that plays out practically:

🏭 Dual Production Lines with Namespaces
Imagine two namespaces:
- production-blue
- production-green
Each holds:
- React + Node Deployments
- Their own Services, ConfigMaps, Secrets, etc.
You serve traffic from production-blue while safely testing new changes in production-green.
🔁 Blue-Green Deployment Strategy (Using Namespaces)
| Phase | Action | 
| ✅ Active | production-blue serves all user traffic | 
| 🧪 Test | You deploy updated code into production-green and validate it | 
| 🔄 Switch | You update your external Service to point to production-green | 
| 🧹 Cleanup | Once stable, you tear down or repurpose production-blue | 
🧠 Why It’s Powerful
- You avoid downtime entirely.
- You get isolated crash-testing without breaking live traffic.
- You can sniff pod traffic between namespaces, use RBAC to restrict access, or even simulate failures using tools like chaos-mesh.

kubens    =>to see all namespaces
kubens <namespace>    =>switch to a namespace
kubectl create ns <namespace>       =>creating a new namespace
kubectl delete ns <namespace>       =>to delete a particular namespace




KUBERNETES OBJECTS:
| Pod | Runs your container(s) 
| Deployment | Manages and scales your Pods 
| Service | Connects and exposes Pods |  
| Namespace | Logical grouping of resources |ex: “Production” or “Testing” | Group it all in prod-webapp or client-x-env. 
| ConfigMap | Injects config data as environment vars or files i.e. For environment configs—like API base URLs, feature flags ports etc
| Secret | Stores sensitive data securely | To store DB passwords or API keys. | 
| PersistentVolumeClaim (PVC) | Requests storage from cluster | Asking IT for a permanent hard drive for your box | 
| StatefulSet | Handles stateful apps like DBs | Like assigning fixed names to boxes: box-0, box-1 | 
| DaemonSet | Runs one Pod per Node | Like putting antivirus software on every machine | 
| Job / CronJob | One-time or scheduled tasks | A temporary worker or a daily shift task ex: run backup every week | 
| Ingress | HTTP routing from outside to Services | A traffic cop deciding which customer goes where | 



there are some types under Kubernetes service object:
🌐 Types of Kubernetes Services
| Type | Visibility | Use Case | Notes | 
| ClusterIP | Internal only | Talk between pods (e.g., frontend calling backend) | Default type, fastest, safest for internal comms | 
| NodePort | External access | Quick exposure for testing or local setups | Opens port on each Node IP (<NodeIP>:<NodePort>) | 
| LoadBalancer | External (cloud) | Real production-grade public access | Requires cloud support (AWS, GCP, Azure, etc.) | 
| ExternalName | DNS-based redirect | Connect to external service (e.g., db.google.com) | No actual pod or selector—just maps DNS names | 



Usecases:
🔧 ClusterIP
Use when:
- Your React app (Pod A) needs to call the Node.js backend (Pod B)
- You don’t want external users touching internal services directly
🧪 NodePort
Use when:
- You want to expose your frontend quickly on http://<NodeIP>:30001
- Good for local setups like Minikube or Docker Desktop
☁️ LoadBalancer
Use when:
- You’re on a cloud platform and want a public IP to serve real traffic
- Kubernetes will provision this automatically through your cloud provider
🌍 ExternalName
Use when:
- You don’t host the service inside Kubernetes (e.g., third-party API or database)
- You just want DNS resolution handled inside your cluster

yaml: a configuration language
YAML (short for YAML Ain’t Markup Language) is a human-readable configuration language that's widely used in DevOps, cloud infrastructure,
Used across tools like Kubernetes, Docker Compose, GitHub Actions, Ansible, and more

for a basic application we need a deployment and a service which helps to access the services
vs code extension: kubernetes   =>template yaml files

1. Deployment = Pod Blueprint
deployment is a collection of pods=>the type,template and configuration of pod
are in template section specifying the pods that are in the deployment
Your deployment YAML defines:
- What to run (image)
- How many to run (replicas)
- Where to run it (selector)
- How to configure it (resources, ports, etc.)
apiVersion: apps/v1
kind: Deployment        
metadata:
  name: backend-deploy    =>name for the app
  namespace: web-app-ns
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend        =>should match with template label(select all pods that have label as backend)
  template:
    metadata:
      labels:
        app: backend      =>should match with selector label(new spinned pods are taken into deployment matching this label with the selector label)
    spec:
      containers:
      - name: backend
        image: docker.io/reponame/your-node-image   =>tell kubernetes where to pull image from
        resources:
          limits:
            memory: "120Mi"
            cpu: "500m"
        ports:
        - containerPort: 3000
        env:
        - name: DATABASE_URL
          value: "somedburl"
        
kubectl apply -f <deploymentfilename>
kubectl apply -f <deploymentfilename> -n <namespace>   =>specify namespace at runtime instead of hardcoding it in yaml

now we have deployment...how do we access them? using services

2. Service = Stable Access Point
Your service YAML:
- Selects pods using selector
- Exposes them via a stable IP and port
- Handles load balancing across replicas
apiVersion: v1
kind: Service
metadata:
  name: backend-service
  namespace: web-app-ns
spec:
  selector:           =>service can always select a deployment or a statefulset
    app: backend
  ports:
  - port: 3000              =>service port...where it should be accessed
    targetPort: 3000        =>pod/containerport...where request goes to

kubectl apply -f <servicefilename>

now whenever we request...it goes through service which takes to one of 3 running pods
since this service is mapped to the pods specified in selector field...it does the loadbalancing work
between these 3 pods

3. Port Forwarding = Local Access
To access your service from your local machine:
do portforwarding to make it accessible from our machine port

kubectl port-forward svc/backend-service 8080:3000

- You can now hit http://localhost:8080 and reach your backend

🔧 Step 2: Backend Config and Secret
Your Node.js app might need:
- A config (like DB URL, mode)
- A secret (DB password)

CONFIGMAP.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-config
  namespace: web-app-ns
data:
  DATABASE_URL: mongodb://db:27017/myapp
  NODE_ENV: production

SECRETS.yaml
apiVersion: v1
kind: Secret
metadata:
  name: backend-secret
  namespace: web-app-ns
type: Opaque
data:
  DB_PASSWORD: bXlzZWNyZXRwYXNz (Base64-encoded)



🐍 Step 3: Backend Deployment + Service
This deploys your Node.js backend and makes it reachable inside the cluster.

BACKEND_DEPLOYMENT.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-deploy
  namespace: web-app-ns
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: backend
        image: your-node-image
        ports:
        - containerPort: 3000
        env:
        - name: DATABASE_URL
          valueFrom:
            configMapKeyRef:
              name: backend-config
              key: DATABASE_URL
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: backend-secret
              key: DB_PASSWORD



BACKEND_SERVICE.yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-service
  namespace: web-app-ns
spec:
  selector:
    app: backend
  ports:
  - port: 3000
    targetPort: 3000
  type: ClusterIP





🎨 Step 4: Frontend Deployment + Service
Let’s serve your React app with Nginx or Vite preview inside the cluster.

FRONTEND_DEPLOYMENT.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-deploy
  namespace: web-app-ns
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: frontend
        image: your-react-image
        ports:
        - containerPort: 80


FRONTEND_SERVICE.yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
  namespace: web-app-ns
spec:
  selector:
    app: frontend
  ports:
  - port: 80
    targetPort: 80
  type: NodePort


Now your frontend is externally accessible, and it can internally call the backend using:
fetch("http://backend-service.web-app-ns.svc.cluster.local:3000/api/...")

To deploy your Kubernetes app on your custom domain Satyam.dev, you’ll need to set up Ingress, an Ingress Controller, 
and configure DNS records to point your domain to your cluster. 

🌐 Step 1: Deploy an Ingress Controller
This is the traffic manager that understands how to route requests from the outside world into your cluster.
Example (using NGINX):
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install nginx-ingress ingress-nginx/ingress-nginx
This creates a LoadBalancer service with an external IP.


📥 Step 2: Create an Ingress Resource
This defines how traffic to Satyam.dev should be routed to your frontend and backend services.

INGRESS_RESOURCE.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: webapp-ingress
  namespace: web-app-ns
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: satyam.dev
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: backend-service
            port:
              number: 3000


🧭 Step 3: Point Your Domain to the Cluster
Once your Ingress Controller is running, get its external IP:
kubectl get svc -n ingress-nginx
Look for the EXTERNAL-IP of the nginx-ingress-controller service.
Then:
- Go to your domain registrar (e.g., Namecheap, GoDaddy).
- Add an A record for satyam.dev pointing to that IP.


🔐 (Optional) Step 4: Add HTTPS with TLS
You can use cert-manager with Let’s Encrypt to automatically provision SSL certificates.
Let me know if you want help setting that up—it’s a great way to secure your app.
